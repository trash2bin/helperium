## TL;DR

- Есть рабочий стек: `api-service` (Python, агент) → `mcp-gateway` → `data-service` (Go, Expression AST → SQL) → Postgres.
- Агент отвечает на вопросы **только через MCP-тулы** (`db_map/db_search/db_get/filter_*`), чистого SQL у него нет.
- Реальная тестовая база: Django-каталог автозапчастей, 407 товаров, 30 брендов, 117 категорий, русскоязычные данные, JSONB (`car_applicability`, `characteristics`).
- Хочу бенч, который на 50–100 прогонах даёт **процент корректных ответов и среднее число ошибок** по классам, чтобы оценивать, работает ли текущая архитектура (core: data-service query engine + MCP-тулы + агент).
- **Не хочу LLM-судью как основу** (×2 цена токенов, сам судья ошибается). Инцидент с Camry показал: критичные дефекты детерминируются.

## Ключевой вывод из инцидента с Camry (полный лог — `backlog/agent_autoparts_55618253-a2cd-4596-b710-c08aba45214c.jsonl`)

Вопрос: «привет у вас есть запчасти для машины камри?»

Трейс (11 tool_calls, 4 LLM-вызова, 22.2s, 34k токенов, $0.21):
```
db_map → db_search("Camry", limit=20) → db_get ×9
```
- `db_search` вернул `"total": 40` + 20 preview (только id/артикул, без цен/названий).
- Агент сделал **9 подряд `db_get`** (по одному товару), контекст раздулся до 8.6k токенов.
- В ответе: показал 4 товара с ценами, «и ещё много других позиций», «Какая модель Camry (V40, V50, V70)?», «BRK-01004 (скорее всего тормозные колодки)».

Верификация по БД (Postgres, tenant `autoparts`):
- V50/V70 **реально есть** в `car_applicability` (не галлюцинация — агент видел их в db_get).
- `total: 40` **был в контексте** (проверено: в `tool_content` без обрезки) — но агент сказал «много позиций», а не «40 товаров» → **упущенный факт**.
- «скорее всего тормозные колодки» — **ложная неуверенность**: в db_get для BRK-01004 было точное `name="Колодки тормозные передние для Toyota Camry V40"`.

**Вывод:** на этой базе агент почти не галлюцинирует (модель сильная, данные консистентные), но **теряет информацию, неуверен там, где данные точны, и перебирает тулы**. Это классы дефектов, которые детерминируются.

## Что проверяется детерминированно (без судьи)

| Метрика | Как считается | Что ловит |
|---|---|---|
| tool_calls / turn | из backlog | перебор тулов (11 на один вопрос) |
| LLM-вызовы, длительность, стоимость | backlog `llm_call` + `turn_end` | деградация, стоимость |
| количество артикулов в ответе vs ground-truth | regex `[A-Z]{3,4}-\d{4,5}` по `final_text` | показал ли все, не потерял ли |
| фактические числа (кол-во, цена, наличие) | сверка с SQL ground-truth (точные строки) | верность фактов |
| `total: N` в tool_result vs «N» в ответе | из backlog + regex | **упущенное знание** (знал 40, не сказал) |
| маркеры неуверенности («скорее всего», «наверное», «вроде») | regex по `final_text` | ложная неуверенность |
| loop-warnings (3+ одинаковых tool_call подряд) | уже есть в `agent_db/bench/parser.py` | зацикливание |

## Что проверяется LLM-судьёй (v2, только для открытых вопросов)

Судья нужен только для семантики, где нет точной строки: «релевантен ли ответ вопросу», «не упущена ли суть». Правила:
- судья — **отдельная модель** (не та, что гоняет агента), прямой вызов через LiteLLM, без тулов агента.
- вход: `{вопрос, tool_results (что агент знал), ответ агента, ground-truth факты}`.
- выход: чек-лист (`верные_факты[]`, `упущенные[]`, `выдуманные[]`, вердикт CORRECT/PARTIAL/WRONG).
- калибровка: раз в N прогонов прогнать «эталонные» пары с известным ответом, посчитать accuracy судьи, скорректировать.

## Почему судье можно давать SQL (агенту нельзя)

- **Агенту** чистый SQL нельзя: безопасность (tenant isolation), архитектура (агент работает через тулы).
- **Судье** в бенче можно: тестовая база, судья не влияет на прод, ground truth нужен именно SQL-ом.
- НО: ground truth готовится **заранее** человеком (пары `вопрос → SQL`), а не генерится судьёй на лету — иначе судья сам станет источником ошибок.

## Архитектура бенча (предлагаемая)

```
1. ground-truth.json        — [{question, sql, expected: {...}, tolerance?}]
2. run_agent.py             — гоняет вопрос через POST /api/chat/{agent} (SSE), собирает final_text + tool_calls
3. exec_ground_truth.py     — выполняет sql против тестовой БД, получает факты
4. deterministic_checks.py  — сверка ответа с фактами (числа, артикулы, total:N, маркеры неуверенности)
5. context_reconstructor.py — из backlog сессии собирает "что агент знал" (tool_results в порядке вызова)
6. judge_llm.py (v2)        — LLM-судья для открытых вопросов
7. report.py                — агрегация: % CORRECT/PARTIAL/WRONG, среднее по классам, дельта между прогонами
```

## Открытые вопросы (нужна экспертиза коллеги)

1. **Приоритет метрик**: что важнее для оценки «работает ли архитектура» — точность фактов, полнота, стоимость, скорость? (моё мнение: сначала точность+полнота, потом стоимость).
2. **Ground truth**: пары `вопрос → SQL` писать вручную (стабильно) или генерить судьёй (масштабируемо)? Сколько вопросов достаточно для 50–100 прогонов (10? 30? 50?).
3. **LLM-судья**: стоит ли вообще, или на 80% хватает детерминированных проверок? Если да — как калибровать, чтобы не доверять на слово.
4. **Изоляция данных**: тестовая база статична (seed) или пересоздаётся каждый прогон? Как избежать «агент запомнил ответы» при повторах?
5. **Что считать «ошибкой»**: несоответствие числа? пропущенный артикул? лишний текст? нужна шкала строгости.
6. **Регрессии**: как сравнивать прогоны между собой (после рефакторинга)? Нужны ли «золотые» прогоны?
