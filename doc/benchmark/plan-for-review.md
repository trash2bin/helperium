# План: бенч для оценки «работает ли core-архитектура» — без LLM-судьи как основы

> Для ревью старшим коллегой. Кратко: что мерить, как, чего не хватает в логгировании, открытые вопросы.

## Контекст за 30 секунд

- Стек: агент (Python) → MCP-тулы → data-service (Go) → Postgres. Агент отвечает только через тулы (`db_map/db_search/db_get/filter_*`), чистого SQL у него нет (безопасность).
- Тестовая база: каталог автозапчастей, 407 товаров, русские данные, JSONB.
- Хочу: на 50–100 прогонах получать **% корректных ответов и среднее ошибок по классам**, чтобы видеть, работает ли core после рефакторинга.

## Главная мысль

**LLM-судья — не фундамент, а v2.** Инцидент с Camry показал: все три дефекта, которые реально происходят, детерминируются без модели.

| Дефект (реальный кейс Camry) | Как мерить без судьи |
|---|---|
| Перебор тулов: 11 tool_calls на «что есть для Camry?» (9× db_get) | счётчик tool_calls из backlog |
| Упущенный факт: знал `total:40`, сказал «много позиций» | `total:N` в tool_result vs ответ; число артикулов в ответе vs ground-truth |
| Ложная неуверенность: «скорее всего колодки» при точном `name` в контексте | regex маркеров («скорее всего», «наверное») по ответу |

**Почему так:** у tool-based агента 80% «качества» — это (а) правильные тулы с правильными аргументами, (б) верные числа/артикулы из БД, (в) полнота (донёс ли всё, что знал). Всё это — точные строки/числа, их можно сверять с ground-truth SQL без LLM.

## Три уровня (по возрастанию сложности)

### Уровень 1 — «Архитектурные» метрики (уже почти есть)
Из `turn_end` + `llm_call` backlog, детерминированно:
- tool_calls/turn, llm_calls/turn, duration, cost, tokens
- tool_errors, empty_results, empty_rounds, iterations
- loop-warnings (уже в `agent_db/bench/parser.py`)

Это отвечает: **«работает ли конвейер, не деградировал ли»** — быстро, дёшево, стабильно.

### Уровень 2 — «Фактическая точность» (главный, тоже без судьи)
Ground truth заранее: пары `{question, sql}` (пишет человек). На прогоне:
- выполняем SQL → получаем факты (числа, артикулы, имена)
- сверяем ответ агента: число упомянуто? артикул есть в БД? количество совпадает?
- **детерминированные проверки**: regex артикулов, поиск чисел, `total:N` vs ответ

Отвечает: **«правильно ли агент достал и донёс данные»**. Это ядро бенча.

### Уровень 3 — LLM-судья (v2, только открытые вопросы)
Для семантики без точной строки («релевантен ли ответ», «упущена ли суть»).
- судья — отдельная модель, прямой вызов, вход: `{вопрос, tool_results, ответ, ground-truth}`
- чек-лист: верные/упущенные/выдуманные факты + вердикт
- калибровка: прогон по эталонным парам, accuracy судьи

## Состояние логгирования
Исторические gaps частично закрыты: `final_text` теперь пишется в `turn_end` и в отдельный bench-log, а runner сохраняет отдельную JSONL-запись и для инфраструктурных ошибок. Полный контекст LLM по-прежнему не записывается в обычный backlog и остаётся осознанным ограничением: LLM-судья v2 должен получать только разрешённый тестовый контекст, а не production-подобные prompts.

Упорядоченная последовательность tool calls берётся из SSE и сохраняется в bench-log. Для новых изменений требуется сохранять это свойство и добавлять unit-тесты для success- и error-путей.

## Открытые вопросы к коллеге (критично)

1. **Сколько вопросов** для 50–100 прогонов: 10, 30, 50? (зависит от: хочу видеть регрессии после рефакторинга; вопросы должны покрывать разные типы тулов: filter, grep, get, related).
2. **Ground truth вручную или генерация?** Моё: вручную (стабильно, SQL пишет человек один раз). Генерация судьёй — риск внести ошибку судьи.
3. **Шкала строгости:** что считать «ошибкой» — несовпадение числа / пропущенный артикул / лишний текст / неправильный бренд? Нужна явная шкала (например: полное совпадение = 1.0, пропуск артикула = 0.5, выдуманный = 0).
4. **Изоляция:** статичная база (один seed на все прогоны) или пересоздавать? Агент может «запомнить» ответы при повторах — как избежать (перемешивать вопросы, менять формулировки)?
5. **Что важнее для «работает ли архитектура»:** точность, полнота, стоимость, скорость? (моё: точность+полнота первичны, стоимость вторична — но если рефакторинг ускорил за счёт точности — это плохо, надо смотреть вместе).
6. **Нужны ли «золотые» прогоны** до рефакторинга, чтобы сравнивать дельту?
7. **Стоит ли судья вообще**, или на Уровнях 1–2 закрываем 90% задач? (я склоняюсь к «да, но v2»).
