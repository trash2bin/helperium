# L2 Linux: py-spy профилирование горячего пути — где живут 27–45 мс на вызов LLM

Стенд: нативный Linux (`ivan@192.168.1.49`), `API_WORKERS=8`, Redis-сессии, direct transport.
Дата: 2026-10-07. Вопрос: `llm_duration_ms` показывает 27–45 мс на вызов, а stub-LLM отвечает за 1–5 мс.
Куда уходит разница?

## Результат одной строкой

**Полный перерасчёт токенов истории перед каждым вызовом модели.** `_context_token_count`
(`agent/loop.py`) вызывается из `_run_limit` перед **каждым** model call (~3 раза за ход);
каждый вызов = `litellm.token_counter` → tiktoken encode **полной** истории (32.6% активного
CPU в профиле) + `json.dumps(tools)//4`. Стоимость растёт с длиной истории — отсюда рост p95
на 5→40 rps (+27 мс) и позиция колена.

## Профиль (py-spy, 40 rps, 494 сэмпла active)

| Доля | Функция | Что это |
|---:|---|---|
| 32.6% | `encode (tiktoken/core.py)` | токенизация истории |
| ~9% | `count_tokens`/`_count_messages`/`_count_function_call_tokens` (litellm/token_counter.py) | обёртка над tiktoken |
| 22.1% | `run (asyncio/runners.py)` | event loop (в C, не раскладывается) |
| 2.8% | `iterencode (json/encoder.py)` | JSON-сериализация |
| — | pydantic/anyio/h11/httpx2 | обычная работа per-request |

OTEL/urllib3/protobuf в чистом профиле: **0 сэмплов**. Ранний профиль (51 сэмпл) с
urllib3/`_encode_span` был артефактом методики, а не измерением.

## Гипотезы, которые умерли

- **TIME_WAIT/httpx client churn не был узким местом.** Чистый A/B (см. ниже): колено
  61.69 rps в обоих вариантах, 40 rps 266 vs 267 мс — идентично. 9188 TIME_WAIT на loopback —
  копейки для ядра, connect на loopback — микросекунды.
- **OTEL-экспорт в пустоту — не объяснение 27–45 мс**, хотя его чинить было правильно
  (см. ниже). Вклад на 40 rps в пределах шума (263 vs 267).

## Ловушки py-spy на нативном стенде (Python 3.13)

1. **resource_tracker вместо воркера.** `pgrep -P <мастер> | head -N` выбирает первые дети —
   среди них `multiprocessing.resource_tracker` (ничего не делает) → «Samples: 0». Правильно:
   держатели сокета 8081 из `ss -ltnp` минус мастер.
2. **ptrace-pause ненадёжен на 3.13.** `py-spy record` без `--nonblocking` даёт 3 сэмпла за
   20 с (100 Hz) — молча. Правильно: `--nonblocking` (process_vm_readv) — тогда 494+ сэмплов.
3. **sudo обязателен**: `kernel.yama.ptrace_scope=1`, py-spy из SSH-шелла не родитель воркеров.
4. Запись пишется в файл только в конце `--duration` — проверять размер файла по ходу нельзя.

## OTEL на стенде: мерил сам себя (чинить было правильно)

`OTEL_ENABLED` дефолт true, `OTEL_SDK_DISABLED` не задавался → экспортёр ретраил protobuf-батчи
в отсутствующий коллектор (`localhost:4318`) — фон, не зависящий от трафика. `HTTPXClientInstrumentor`
оборачивал каждый httpx-запрос. Фикс: `OTEL_SDK_DISABLED=true` в `scripts/stress/stand.env` +
`export OTEL_SDK_DISABLED` в `start-stand.sh` (plain assignment без export не наследуется
процессами стенда — проверено по `/proc/<pid>/environ`). Стенд — измерительный инструмент:
он не должен нести трейсер, меряющий сам себя.

## Реализованный фикс: кэш токенов (внутренний, без изменения контракта)

`_context_token_count` (`agent/loop.py`) теперь кэширует счёт по сообщению
(транскрипт append-only внутри хода — инвариант держится конструкцией
`Transcript.append`) и по tool-схеме (константен внутри хода). `_run_limit`
вызывает подсчёт перед каждым model call — тикен-работа режется на размер
истории вместо полного пересчёта.

Микро-бенчмарк в коде (мак, синтетика 56 ходов × 3 проверки, реальный
`litellm.token_counter` → tiktoken, финальный контекст ~14.5k токенов):

| Путь | Время | Вызовы |
|---|---:|---:|
| OLD (полный пересчёт, fresh loop на каждый подсчёт) | 193.0 ms | 168 |
| NEW (кэш по сообщению + tool-схема) | 126.1 ms | 168 |

Ускорение **1.5×** на пути подсчёта токенов; per-call overhead литема
(валидация, `cleanup_none_field_in_message`) остаётся. Эффект на колено
нужен стенд-прогон (ПК выключен — отложено).

Дрейф оценки: `litellm.token_counter` не аддитивен (полный батч 14045 vs
сумма по одному 14711 на 223 сообщениях — per-message overhead). Кэш даёт
**консервативный** дрейф ~+3 токена на сообщение (+3.6% на 14.5k) — для
guardrail (`limit_reached` при превышении) это безопасное направление:
порог срабатывает на чуть раньше, не позже.

Тесты (`test_loop.py`, 5 новых): только новые сообщения проходят через
счётчик; tool-схема кодируется один раз; откат на character-fallback тоже
кэшируется; защитный сброс при нарушении append-only; итог с кэшем равен
пересчёту с нуля на аддитивном фейке. Suite api-service: 881 passed.
