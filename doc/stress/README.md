## TL;DR

Три воспроизводимых утверждения, а не одно число:

1. **Ёмкость:** «N rps / M одновременных чатов при p95 ≤ T и error rate ≤ 1% на конкретном железе».
2. **Стабильность:** «на 70% найденной ёмкости система отработала 48 часов без монотонного дрейфа
   p95, RSS, дескрипторов и горутин».
3. **Устойчивость:** «при зависании зависимости и при превышении ёмкости в 10× система деградирует
   предсказуемо (429/retryable/sanitised), не теряет ресурсы, возвращается к baseline после снятия
   перегруза и не задевает чужие tenant'ы».

Продающая часть — не цифра, а связка: **нашли knee → показали причину (per-tenant сериализация
MCP-сессии, лимиты соединений SQLite, синхронный backlog) → подтвердили сдвигом tenant-фанаута и
повтором с фиксом.** Число без этого нарратива интервьюер проверить не может. Отсюда фаза 0 (§0) и
фаза 6 (§13): без них связка не доказывается.

Правило харнесса: **число без манифеста прогона не считается доказательством.** Отчёты с разными
`environment`-полями не сравниваются вообще (см. §6).

## §0. Фаза 0 — инструментация измерительного прибора (сделано)

Верификация v3→v4 показала, что **основная метрика ёмкости была невычислима**: единственный источник
серверной латентности LLM, `llm_call.duration_ms`, писался нулём, а объявленные метрики
`llm_duration_ms` / `llm_calls_total` / `llm_token_usage` / `llm_cost_total` никогда не
инкрементились. То есть `platform_overhead = t_complete − Σ LLM-latency` вычитал нули и молча
превращался в `t_complete` — то есть в тот критерий, который §7 сам называет неверным.

Фаза 0 закрывает это до любого прогона (изменения в `api-service`, с regression-тестами):

| Что | Где | Зачем |
|---|---|---|
| `duration_ms` измеряется вокруг `provider.complete()` и пишется в backlog | `agent/loop.py` (`_record_provider_response`) | источник `platform_overhead` |
| `llm_calls_total` / `llm_duration_ms` / `llm_token_usage` / `llm_cost_total` инкрементятся | `agent/loop.py` | латентность и токены видны и в Prometheus, а не только в backlog |
| `mcp_lock_wait_seconds` (histogram) и `mcp_lock_timeouts_total` | `agent/mcp_client.py` вокруг `conn.call_lock.acquire()` | сериализация на tenant становится **измеренной**, а не выведенной из сдвига knee |
| `session_id` пишется в запись `llm_call` | `backlog.py` | join без парсинга имени файла |

Тесты, фиксирующие контракт (падают при откате): `test_backlog.py::test_llm_call_record_is_joinable_to_its_session`,
`agent/test_loop.py::test_llm_call_records_measured_latency_and_live_llm_metrics`,
`agent/test_mcp_client_metrics.py::TestLockWaitObservability`.

**Где это живёт.** Эмиссия метрик не в доменном цикле: `loop.py` зависит от узкого порта
(`protocols.LoopRecorderPort`), реализации — в `agent/adapters.py`
(`_BacklogRecorder` — durable evidence, `_PrometheusLlmCallMetrics` — телеметрия,
`_TurnRecorder` — один вызов на событие с fan-out в оба стока). Оркестратор строит рекордер
на ход (`build_turn_recorder()`) и сам пишет turn-события через него, а не через глобальный
синглтон — так у каждого события ровно один путь к стоку. Обратная сторона этого шва —
требование к отчёту: поля `turn_end`/`llm_call` нельзя терять по дороге, поэтому их набор
зафиксирован в порту и в тесте адаптера (`final_text`, `empty_rounds`, `iterations` и др.
уже однажды потерялись при первом проходе и были пойманы тестом).

Осознанно **не** сделано в фазе 0: публичный текст ошибки на таймауте лока по-прежнему совпадает с
текстом таймаута выполнения (`_timeout_error_result`). Различать их на стороне клиента — изменение
публичной поверхности; для харнесса достаточно серверных метрик.

## 1. Что меряем: слои и контракт метрик

| Слой | Трафик | LLM | Что доказывает |
|---|---|---|---|
| **L0** control-plane | `/health`, `/metrics` (с API bearer), валидация `X-Tenant-ID`, `/admin/*` | нет | базовый оверхед рантайма, sanity харнесса |
| **L1** data-plane | MCP tool call: `mcp-gateway` → `data-service` → tenant DB | нет | пропускная способность ядра (query engine, tenant isolation) |
| **L2** orchestration | `POST /api/chat` SSE со stub-LLM нулевой задержки | stub | потолок api-service: SSE, история сессии, MCP-клиент |
| **L3** product-shape | то же с заданной латентностью LLM (p50 800 ms, p95 2.5 s) | stub / scripted / local | сколько одновременных чатов держит платформа |
| **L4** soak + overload | L3 длинной дистанции + инъекция отказов + abuse-сценарии | stub / local | деградация во времени, поведение на пределе |

Потолки независимы: рантайм, LLM-провайдер, tenant DB. Потолок провайдера клиенту не принадлежит,
поэтому L3 измеряется с **управляемой** латентностью, а не с «как получится у провайдера».

**Важно для L1:** per-tenant `call_lock` живёт в **api-service** (`agent/mcp_client.py`), а L1 и
вынесенный MCP-драйвер бьют прямо в `mcp-gateway`. Значит knee на L1 физически не может быть
«сериализацией MCP-сессии»: L1 измеряет gateway + data-service + БД. Сериализация наблюдаема только
на L2/L3 (или при прогоне MCP-драйвера через api-service). В отчёте это пишется явно, иначе knee L1
будет неверно интерпретирован.

### Контракт метрик (первый вопрос к любой цифре)

У продукта три разных «начала» и два «конца», и «1 rps» без уточнения бессмысленно:

| Метрика | Определение | Почему нужна |
|---|---|---|
| `rps` | число **новых ходов** (`POST /api/chat`), принятых в обработку | номинал нагрузки; сессии и повторы в него не входят |
| `ttfe_session` | время до первого SSE-события (`session`, capability handshake) | сетевой sanity, не отзывчивость |
| `ttfe` | время до первого **содержательного** события (после `session`) | отзывчивость виджета |
| `ttfe_tool` | время до первого `tool_call` | когда кажется, что «думает» |
| `t_complete` | время до события `done` / закрытия стрима | время хода целиком |
| `platform_overhead` | `t_complete − Σ LLM-latency`, где LLM-части — фактические `duration_ms` из backlog (`record_llm_call`) | **первичная** метрика ёмкости платформы |
| `platform_overhead_model` | то же, но LLM-части = номинальные p50/p95 профиля | расхождение с `platform_overhead` — оценка очереди прибора (§4) |

- **`ttfe` считается после `session`.** Первым в стрим приходит событие `session` (capability
  handshake, вместе с `X-Session-Token`), и наивное «время до первого SSE-события» измерило бы
  рукопожатие, а не продукт. Полный набор событий: `session`, `tool_call`, `tool_result`, `final`,
  `error`, `done` (+ `audio` для голоса); `done` эмитится из `chat.py`, а не из `sse.py`.
- **Главный признак «мерили прибор» — две величины рядом, но подтверждение точное.** Когда stub
  насыщается, его собственная очередь попадает внутрь `duration_ms` (замер идёт снаружи HTTP-вызова),
  поэтому фактический `platform_overhead` **занижается**, а knee выглядит лучше, чем есть. Поэтому
  §4 требует от заглушки собственных таймингов на запрос (`arrival_ms`, `service_start_ms`,
  `service_ms`): `queue_wait = service_start − arrival` даёт детерминированный признак, а
  `platform_overhead_model` остаётся дешёвой перекрёстной проверкой.
- **`retryable` клиенту не отдаётся.** В SSE `error` есть только `type`, `text` и `correlation_id`;
  флаг `retryable` живёт в structured-записи backlog (`outcome.context.retryable`), а текст ошибки
  локализован по `Accept-Language` (ru/en). Значит требование §7 «100% retryable» доказуемо только
  через backlog, и **классифицировать ошибку по тексту нельзя** — только по структурным полям.
- **Проверенный факт:** LLM-транспорт **не стриминговый**. В `litellm_provider.complete()` в `kwargs`
  уходят только `model` / `messages` / `temperature` / `timeout` / `custom_llm_provider` / `api_base`
  / `api_key` / `extra_body`; ключа `stream` нет ни в одном пути (все `stream=True` в репо — SSE-клиенты
  bench/e2e и MCP-transport). Отсюда: в модели латентности нет «TTFB + каденс токенов», ход — это
  **раунды**, `t_complete ≈ Σ(LLM_latency + tool_latency + overhead)`, число раундов ограничено
  `AGENT_MAX_ITERATIONS=5`.
- **`t_complete` при грубых событиях практически равен времени всего хода агента**, и «p95 3 s» —
  утверждение про ход целиком, а не про стриминг.

## 2. Модель нагрузки

- **Открытый контур (constant arrival rate)** — основной режим: задаём целевой rps, меряем
  достигнутый, латентность и ошибки. Закрытый контур (N виртуальных пользователей) — отдельное
  утверждение «сколько одновременных сессий держит», его латентность зависит от числа VU.
- **Knee, а не максимум.** Лестница стадий (5 → 10 → 20 → 40 → 80 …); ёмкость = последняя стадия,
  где `p95 ≤ T` и `error ≤ 1%`. «Максимум» — точка, где система уже деградировала, защищать её
  бессмысленно.
- **Разрешение knee — бисекция.** Точность «×2» («между 40 и 80») числом не является: между
  последней прошедшей и первой упавшей стадией запускается бисекция до ±10%.
- **Warm-up исключается из статистики.** Первые минуты стадии (прогрев пулов, планов запросов,
  JIT/кешей) отбрасываются; стадии длинные (5–10 мин) и выровнены с интервалом скрейпа Prometheus
  (**15 s**, `infra/docker/prometheus/prometheus.yml`).
- **Два режима лестницы** (вместо рандомизации порядка стадий):
  - `fresh-ladder` — стек и volume пересоздаются между стадиями: чистая кривая ёмкости;
  - `price-of-time` — растущая лестница без сброса на одном инстансе: старение системы
    (рост БД сессий, прогрев памяти) не шум, а **измеряемая величина** отдельного отчёта.
  Рандомизация порядка не используется: она ломает форму кривой и смешивает два эффекта.
- **Coordinated omission.** Отсутствие компенсации занижает перцентили при открытом контуре.
  Канонический источник перцентилей — **raw JSONL харнесса**, не агрегат инструмента: в нём
  лежат `planned_ms` и `actual_ms` на каждый запрос, и компенсация считается в одном месте (§10).
  Сигнал «генератор насытился» — `dropped_iterations > 0` (k6) / пропущенные тики расписания
  (Python-драйвер).
- **Невалидная стадия — это действие, а не вердикт.** Правило: `dropped_ticks > 0` → пул (сессий и
  VU) умножается на 2 и стадия повторяется; только после двух неудачных расширений стадия
  объявляется невалидной. Иначе каждая невалидная стадия означает ручной перезапуск, а knee рискует
  оказаться knee'ом генератора.
- **Расширение пула лечит только одну из двух причин невалидности (измерено 2026-09-27).** Правило
  выше предполагает, что слотов не хватило. Если же генератор исчерпал CPU, каждый новый воркер
  добавляет ещё один busy-wait хвост и стадия становится хуже, а не лучше: на 160 rps пул был
  удвоен дважды до 672 воркеров, и прогон закончился 117% одного ядра, 19 пропущенными тиками и
  лагом p99 6.3 ms — то есть knee оказался бы knee'ом прибора. Поэтому невалидность по CPU
  (`cpu_s / duration_s >= 0.8` ядра) не расширяется: стадия объявляется невалидной сразу,
  с этой причиной в отчёте. Обе величины берутся из **измеренного окна**: CPU-часы
  снимаются в момент, когда стартует первый измеренный тик (границу ловит сам воркер — без
  монитор-потока и без лишних часов), а знаменатель — окно, которое эти тики занимают. Делить CPU
  всей стадии на окно было завышением (прибору приписывалась работа прогрева, ×1.25 на прогоне из
  §10), а делить измеренное окно на всю стадию — занижением: генератор, выехавший в 0.85 ядра внутри
  окна, при 300 s стадии и 60 s прогрева даёт 0.68 по стадии и проходит гейт — ровно та ступень,
  которую нельзя лечить расширением пула. Числитель и знаменатель теперь из одного окна, а `cpu_s`
  по всей стадии печатается отдельно. Цена воркера не косметическая: калиброванный хвост на Darwin — 10.5 ms
  (квантование таймера), при периоде ~1 s на воркер это ~1% ядра на воркер, и 168 воркеров стоят
  114% ядра. На Linux `time.sleep` спит по `clock_nanosleep` с субмиллисекундным пробуждением,
  поэтому там ожидаемый хвост ~1 ms и та же ширина пула — порядка 0.1 ядра (проверить на стенде).
  Практический вывод для §6: при широких пулах генератор выносится на отдельный хост
  (`generator_host` в манифесте), иначе он отбирает CPU у измеряемых сервисов.
- **Пул VU и пул сессий считаются из критерия, а не из наблюдённого p95.** `pool_size =
  ceil(target_rps × (T + margin)) × headroom`, пересчёт на каждую стадию лестницы и на бисекцию.
  Почему из критерия: если считать из наблюдаемого p95 прошлой стадии, пул растёт вместе с той
  деградацией, которую мы ищем. Для 40 rps и T + margin = 4 s это ≥160 слотов; при 80 rps — ≥320.
  Фиксированное значение в профиле — только нижняя граница для малых стадий.
- **Повторяемость.** Headline-число — медиана 2–3 прогонов, разброс в отчёте отдельной колонкой.
  Один прогон головным числом не публикуется.
- **Смета вызовов на ход — не только нагрузочный профиль.** Кроме вызовов самого профиля каждый ход
  содержит фиксированный префикс, который тоже берёт per-tenant `call_lock`, и его нужно считать в
  аналитическом прогнозе (см. §3):
  - `db_map` — schema preload **на каждый ход** (`orchestrator.py`), результат обрезается до 10 000
    символов и вклеивается в контекст как авторитетное system-сообщение;
  - `list_tools` — на каждый ход, под своим `list_lock` (`call_lock` не берёт);
  - при открытии коннекта — `GET mapping/schema` и `list_tools` (в статистику стадии не входят, но
    входят в прогрев).

## 3. Профиль нагрузки: декларативный, версионируемый

Профиль — JSON в репе (аналог `agent_db/bench/cases/autoparts.json`).

```jsonc
{
  "profile_version": 3,
  "name": "chat-mixed-v3",
  "target_layer": "L3",
  "tenants": { "count": 8, "distribution": "round_robin", "scope": "separate" },
  "sessions": {
    "pool_size": 160,              // нижняя граница; на стадии = rps × (T + margin)
    "recycle_after_turns": 40,     // ниже max_user_turns=50
    "recycle_after_seconds": 1800,
    "min_interval_ms": 1200        // > серверного ABUSE_MIN_INTERVAL_MS=1000, см. ниже
  },
  "arrival": { "model": "constant", "rps": 20, "duration_s": 600, "warmup_s": 120 },
  "clients": { "source_ips": 1, "generators": 1 },   // >1 требует macvlan/IP-алиасов (§5)
  "llm": { "substrate": "stub", "provider_concurrency": 256, "p50_ms": 800, "p95_ms": 2500 },
  "workload": [
    { "weight": 0.4, "name": "one_tool",   "tools": ["db_get"], "history_turns": 0 },
    { "weight": 0.4, "name": "search_get", "tools": ["db_search", "db_get"], "history_turns": 3 },
    { "weight": 0.2, "name": "heavy",      "tools": ["db_map", "db_search"], "repeat": {"db_get": 6}, "history_turns": 8 }
  ],
  "budget_preset": "off"           // off | on — см. §5
}
```

Решения и почему:

- **Имена тулов остаются в профиле, но харнесс их валидирует, а не «адаптируется».** В v3 было
  написано «харнесс не знает тулов поимённо», что противоречило JSON в том же разделе. Честная
  формулировка: профиль называет тулы, харнесс сверяет их с живым `/mcp/manifest` и **явно
  отказывается** запускаться, если тула нет (и подсказывает ближайшее имя). Это и есть контракт
  §12.2 «профиль адаптировался **или явно отказал**» — реализуемо только второе. Текущая
  поверхность: `db_map`, `db_describe`, `db_search`, `db_filter`, `db_get`, `db_related` +
  `filter_{entity}`; в composite-режиме имена получают префикс `{tenant}__`.
- **`heavy` не упирается в потолок тулов.** `AGENT_MAX_TOOL_CALLS=10` — жёсткий терминатор хода, а
  v3-профиль `db_map + db_search + 8×db_get = 10` стоял ровно на границе: одно отклонение агента — и
  объявленная нагрузка превращается в усечённый ход. В v4 `repeat: 6` (= 8 вызовов, запас 2).
  Дополнительно: ссылка v3 на «Camry-прецедент, 11 tool calls» больше не воспроизводима — 11 вызовов
  физически невозможны при лимите 10.
- **Ход может закончиться не по итерациям, а по трём другим лимитам.** `AGENT_MAX_ITERATIONS=5`,
  `AGENT_MAX_TOOL_CALLS=10`, `AGENT_MAX_TURN_TOKENS=8000`; превышение любого даёт
  `LoopOutcome(kind="limit_reached")` с текстами `MODEL_CALL_LIMIT` / `CONTEXT_LIMIT` /
  `TOOL_CALL_LIMIT`, и клиент видит **HTTP 200 + SSE `error`**. Отчёт обязан печатать, каким
  терминатором кончился ход: без этого «error rate» смешивает рабочую деградацию, кривой профиль и
  реальные отказы.
- **Рециклинг: дрейфа истории нет, и это надо сказать честно.** В v3 было «история отрастает до 40
  ходов и падает в ноль». В коде история и так обрезается: хранилище хранит последние
  `DEMO_HISTORY_TURNS=8` ходов (`max_turns=settings.history_turns`), и промпт собирается из этого
  среза. То есть рециклинг на 40 ходах сбрасывает счётчик ходов сессии и состояние анти-абьюза, но
  **не** размер промпта. Реальное ограничение размера промпта — 8000 токенов на ход, причём первым
  туда влезает schema preload (до 10 000 символов ≈ 2500 токенов), поэтому фактическая глубина
  истории в промпте часто меньше объявленной. Поэтому:
  - в отчёт идёт **фактический `prompt_tokens`** из записи `llm_call` (он живой и в backlog, и в
    Prometheus), а объявленный `history_turns` — только как план;
  - превышение `AGENT_MAX_TURN_TOKENS` = терминатор `CONTEXT_LIMIT`, а не «длинный ход».
- **`min_interval_ms` — зеркало серверной проверки, и нарушение молчит.** `ABUSE_MIN_INTERVAL_MS=1000`
  считается от принятого ingress user turn, а отказ приходит как **HTTP 200 + SSE `error`** (не 429).
  Поэтому клиентский интервал в профиле взят с запасом (1200 ms), и харнесс обязан считать такой
  ответ отказом, а не успехом. Это же ограничение действует на прогрев: если гнать ходы одной сессии
  чаще 1 c, «прогревающий» ход молча не применится и история не построится.
- **Пул сессий с рециклингом вместо `unique_per_request`.** Уникальная сессия на запрос физически не
  может иметь историю (она пустая), а её per-session бюджет никогда не срабатывает — то есть такой
  профиль не экспонирует ни историю, ни per-session лимитер.
- **`pool_size ≥ пиковой одновременности` + одна in-flight реплика на сессию.** Один ход
  сериализуется per-session локом агента (`orchestrator` держит лок на весь ход), а интервал в
  профиле отвергает второй запрос в ту же сессию раньше, чем он дойдёт до обработки. Если пул меньше
  одновременности, драйвер сам становится потолком.
- **Прогрев истории распараллелен, ограничен per-IP бюджетом и поэтому лежит в смете.** Веса профиля
  дают ≈2.4 прогревающих хода на сессию; пул 320 — это ≈800 ходов, то есть ≈15 минут wall-clock на
  одном source IP при `budget_preset: on` (1 rps, burst 20), и делится на число IP.
- **Аналитический прогноз knee пишется до прогона.** Для L2/L3 потолок одного tenant'а —
  `1 / p95(tool_latency)` вызовов в секунду, потому что все tool-вызовы хода (включая `db_map`
  preload) идут через один `call_lock` одного соединения; на ход приходится
  `1 (preload) + N (профиль)` вызовов, значит потолок ходов на tenant ≈ `1 / (p95_tool × (1 + N))`;
  на `tenants.count = 8` с раздельными соединениями — в 8 раз выше. Замер `p95(tool_latency)` на L1
  даёт предсказание **до** лестницы, и совпадение/расхождение с найденным knee — это и есть причинный
  вывод, а не «knee сдвинулся при фанауте». В отчёт колонкой: «предсказано / найдено».
- **Composite-scope — отдельная ось, а не следствие `count`.** Лок — на **tenant set**: 8 отдельных
  соединений = 8 локов, один composite-scope из 8 tenant'ов = **один** лок на всех, и потолок при
  фанауте не растёт. Это самая злая точка продукта (composite-агент — реальная фича), поэтому
  `tenants.scope: "separate" | "composite"` в профиле и пара отчётов.
- **Multi-tenant обязателен.** `tenants.count` + `distribution` — потому что главный вопрос дизайна:
  «сдвигается ли потолок при N tenant'ах». Tenant'ы пре-провижнятся (seedgen + register) до прогона:
  создание tenant'а **во время** нагрузки измеряет registration path, а не ёмкость.
- **`cold_start` вынесен из capacity-профиля.** Холодные старты (MCP handshake, circuit breaker)
  селятся в хвост распределения и портят p95/p99, а значит и knee. Отдельный профиль
  `cold-start-v1` и отдельный отчёт.
- **`provider_concurrency` назван явно, и серверного лимита для него нет.** В `ProviderPool` семафора
  нет: api-service не ограничивает число одновременных LLM-вызовов, поэтому единственный потолок
  параллелизма — сама заглушка. Значит этот параметр обязан быть заведомо щедрым, а его очередь —
  видимой (§4), иначе knee заглушки будет выдан за knee платформы.
- **Ещё два общих файла, которых нет в смете v3** (проверять в фазе 3, не в фазе 1): `spending.py`
  держит глобальный `threading.Lock` и перезаписывает `.data/spending.json` **на каждый model call**
  (при 20 rps × 3 раунда — 60 перезаписей файла в секунду, общего для всех tenant'ов); `agents.sqlite`
  берёт второй глобальный `threading.Lock` на каждую операцию, включая чтения.

**Аргументы тулов берутся из фикстуры, а не из профиля и не из манифеста (проверено живьём 2026-09-27).**
`/mcp/manifest` отдаёт только `name`, `display_name`, `endpoint`, `description` — метаданных аргументов
в нём нет: JSON-схему, которую видит MCP-клиент, gateway собирает из конфига тенанта
(`mcp_tools[].params`) при регистрации тула. Значит значения аргументов взять неоткуда, кроме
фикстуры: `agent_db/stress/fixtures/<scenario>.json` (версия, сценарий сида, карта `тул → аргументы`),
а профиль ссылается на неё полем `fixture`. Одна фикстура обслуживает несколько профилей; покрытие
сверяется при запуске, лишние записи допускаются. Без этого L1-стадия вырождается в поток `isError`:
`db_get` с несуществующим id отвечает `isError: true` за ~5 мс, и error rate 100% даёт «ёмкость 0 rps».

Что ещё показал тот же прогон (изолированный стенд, `sqlite-testseed`, 6 тулов в манифесте):

- имена параметров надо брать из конфиггена, а не угадывать: у `db_search` это `pattern` (не
  `query`), у `db_filter` поля передаются **верхним уровнем**, а не в объекте `filters` — обе первые
  версии фикстуры падали 400;
- ошибку надо считать по MCP-`isError`, а не по успеху транспорта: `MCPCallResult.success` в
  e2e-хелпере означает «HTTP/SSE не бросил исключение», и 404-payload проходит с ним как успех;
- `filter_{entity}` из §3 отдельным тулом в живом манифесте не появляется (он строится только при
  настроенных filterable-правилах), а `db_related` в этом сценарии вызвать нечем — у всех сущностей
  `relations: null`;
- живой `db_map` публикует для `group` фильтруемые поля `name` и `speciality`, а `/q/filter` принимает
  только `name` («valid filterable fields for group: name»). Это расхождение продукта, не харнесса;
  фикстура ходит по `name`.

- `filter_{entity}` из §3 отдельным тулом в живом манифесте не появляется (он строится только при
  настроенных filterable-правилах), а `db_related` в этом сценарии вызвать нечем — у всех сущностей
  `relations: null`;
- живой `db_map` публикует для `group` фильтруемые поля `name` и `speciality`, а `/q/filter` принимает
  только `name` («valid filterable fields for group: name»). Это расхождение продукта, не харнесса;
  фикстура ходит по `name`;
- `/mcp` работает **без состояния**: `initialize` отдаёт 200 без `Mcp-Session-Id`, поэтому MCP-сессии
  не существует и переинициализация в драйвере — защита на случай stateful-развёртывания, а не рабочий
  путь. «Рециклинг сессий» из §3 относится к чат-сессиям пула, а не к MCP;
- `tools/call` отвечает `application/json`, а не `text/event-stream`: SSE-ветка парсера — на случай
  смены негоциации, а `notifications/initialized` отвечает 202 с пустым телом — поэтому пустое тело
  считается ошибкой только у запроса;
- в L1-записях `session_id` пустой осознанно: на этом слое нет чат-сессии, а MCP-сессия не выдаётся.
  Ключ группировки вызовов в один ход — пара (`tenant`, `planned_ms`), уникальная внутри стадии.

## 4. LLM-подложка: 0 токенов, stub как часть прибора

| substrate | Как | Что даёт | Ограничение |
|---|---|---|---|
| `stub` | свой OpenAI-совместимый сервер (**non-streaming**, как и реальный транспорт проекта): латентность p50/p95 + jitter + **latency как функция длины промпта**, лимит параллелизма, детерминированные `tool_calls` | полный pipeline, управляемая кривая «rps ↔ LLM latency» | **не существует в репо — писать с нуля**; качество ответа не проверяется (и не должно) |
| `scripted` | `USE_SCRIPTED_LLM=1` + `SCRIPTED_LLM_PATH=<jsonl>` (+ `SCRIPTED_LLM_RECORD` для записи) | байт-в-байт воспроизводимость | по коду: **только** детерминированная задержка `delay_ms` на строку, без jitter и без распределения; файл перечитывается на каждый ход и **курсор сбрасывается** — скрипт всегда начинается с раунда 1, поэтому многораундовый диалог им не моделируется; исчерпание строк даёт пустой ответ |
| `local` | Ollama (`qwen2.5:0.5b`) или llama.cpp/vLLM | «с реальной моделью» — одна точка | **Ollama в compose нет** (ни сервиса, ни профиля) — поднимать отдельно; `OLLAMA_NUM_PARALLEL` в репо не задан нигде, а его дефолт мал и создаёт скрытую очередь — задавать явно и писать в манифест |

`remote-free` **исключён**: 429 и аутеджи провайдера делают прогон невалидным по нашим же
правилам (§7), а ценность ниже риска. Отдельно: в коде уже есть спец-обход под отказы `nvidia_nim` —
то есть этот провайдер для нагрузки исторически ненадёжен.

Правила, потому что stub — измерительный прибор, а не SUT:

- **Заглушка логирует свои тайминги на запрос**: `arrival_ms`, `service_start_ms`, `service_ms` с
  correlation id, который харнесс кладёт в запрос (маркер в сообщении/заголовке). Это снимает
  двусмысленность §1: `queue_wait = service_start − arrival` и
  `platform_overhead_exact = t_complete − Σ service_ms` считаются точно, без порога «расхождение
  больше T/2». До этого эвристикой остаётся только `platform_overhead_model` (см. §7).
- **Латентность заглушки должна зависеть от длины промпта** (`overhead + prompt_tokens / rate`), а не
  быть константой. Иначе измеряется профиль, которого нет: у нас история режется до 8 ходов и
  8000 токенов, и константная задержка делает этот срез невидимым в `platform_overhead`.
- **Свои метрики заглушки в отчёте отдельной строкой**: глубина очереди, её собственная латентность,
  CPU. Loopback-калибровка (генератор → stub напрямую, мимо SUT) — обязательный preflight с
  требованием **headroom ≥ 3×** от целевого rps; это же готовый ответ на вопрос «вы мерили свой
  генератор?».
- **Contract-тест «имена тулов в JSONL ⊆ манифест» — новый** (его нет; вместе с ним и тест
  «stub соответствует OpenAI-контракту, который ждёт LiteLLM»). Без него scripted-подложка дрейфует
  от профиля молча.

## 5. Бюджеты и лимиты: один пресет для лестницы, второй для ассертов

| Бюджет | Где | Дефолт | Ключ и семантика |
|---|---|---|---|
| `CHAT_RATE_LIMIT` | slowapi: `Limiter(key_func=get_client_ip, default_limits=…)` + `SlowAPIMiddleware`, плюс `@limiter.limit` на трёх chat-роутах | 30/minute | per-IP **и per-path** (`key_style` по умолчанию `"url"`): `/api/chat`, `/api/chat/voice` и `/api/chat/{name}` имеют раздельные бакеты, причём `{name}` — свой бакет на каждый agent name. test-профиль Compose его **не** переопределяет |
| `REPORTS_RATE_LIMIT` | slowapi, `@limiter.limit` на `/reports` | 5/minute | per-IP, независимо от chat-бакета |
| per-session bucket | `TokenBucket.allow()` | `ABUSE_RPS=1.0`, `ABUSE_BURST=5` | ключ — **тройка** `session_id : ip : hash(User-Agent)` (32-битный встроенный `hash`) |
| per-IP bucket (pentest H2) | `TokenBucket.allow_ip()` | `ABUSE_IP_RPS=1.0`, `ABUSE_IP_BURST=20` | ключ `ip:<ip>`, проверяется **первым**; ротация `session_id` его не обновляет |
| `min_interval_ms` / `max_repeated_count` / `max_user_turns` / длина сообщения | `AntiAbuseChecker` | 1000 ms / 3 / 50 / 2000 символов | quality-проверки: отказ приходит **HTTP 200 + SSE `error`**, без `Retry-After` |
| `MCP_RATE_LIMIT_RPS` | mcp-gateway | 10 (burst 20, LRU 10000 IP) | потолок tool-call'ов; в test-профиле поднят до 1000 |
| UA-фильтр | `AntiAbuseChecker._check_user_agent` | enabled | блокирует `curl/`, `python-requests`, `axios/`, `go-http-client` и пустой UA (матч подстрокой, case-insensitive). Генератор обязан слать браузерный UA |
| эвикция in-memory состояния | `TokenBucket` | 4096 записей на оба bucket'а | размер состояния не растёт (проверяется в soak) |

Три следствия для генератора, которые дороже всего игнорировать:

- **per-session bucket ключуется ещё и по IP с UA.** Ротация `session_id` бюджет не обновляет, но
  ротация **User-Agent** обновляет: у каждой тройки свой bucket. Генератор, который перемешивает UA
  на каждый запрос, сам себе выдаёт бесконечный burst — стена 429, которую он обязан встретить, не
  встречается, и прогон оказывается про песочницу генератора. UA фиксируется и пишется в манифест.
- **`CHAT_RATE_LIMIT` — главный ложный потолок.** 30/minute **на путь** — это 0.5 rps на маршрут, на
  порядки ниже любого железа: пока он не поднят, «ёмкость» мерить нечего. При этом высокие
  `ABUSE_IP_RPS`/`MCP_RATE_LIMIT_RPS` в test-профиле (1000) создают ложное ощущение, что бюджеты уже
  сняты.
- **Качество и бюджет различаются по форме ответа.** 429 с `Retry-After > 0` — это бакеты
  (`allow_ip` / `allow`). Quality-отказы — HTTP 200 и SSE `error`. Поэтому «ошибка = статус ≠ 2xx»
  в харнессе неверно by design, и `abuse_blocked_total` инкрементится **только** на quality-отказах
  (`reason=user_agent|message_length|interval|user_turn_quota|repeated_text`), а не на 429-бакетах.
  Ассерт про бюджет опирается на статус 429 и `Retry-After`, а про лимитер целиком — на
  `abuse_blocked_total` **плюс** счётчик 429-ответов (если его окажется мало — добавить
  `abuse_rate_limited_total`, это часть фазы 1).

- **`budget_preset: off`** — измеряем потолок инфраструктуры, и **только этот пресет даёт
  knee-лестницу**. Пресет **перечисляет все бюджеты таблицы с фактическими значениями** в
  манифесте: «подняты» — не спецификация, и через месяц никто не вспомнит, что именно поднимали.
- **`budget_preset: on`** — дефолты Compose: проверяем, что 429 корректен (`Retry-After > 0`,
  latency отказа < 5 ms, соседние IP/tenant не затронуты). При этом пресете 429 — **expected, а не
  error** (§7), а **ladder не запускается вообще**: при 0.5 rps на путь точка перегиба не определена,
  и «найденный knee» был бы knee'ом slowapi.

Многоклиентность при `on` обеспечивается несколькими исходными адресами (macvlan / IP-алиасы на
Linux либо N контейнеров генератора). Подмена `X-Forwarded-For` — не способ обойти лимитер: ключ
берётся из правого непустого XFF только если TCP-peer в `TRUSTED_PROXIES`, иначе — socket IP. Это
отдельный security-кейс.

## 6. Воспроизводимость: манифест делится на environment и code

Без этого `compare` невозможен: регрессию меряют между **разными** коммитами, а значит `code`
обязан отличаться.

| Группа | Поля | Правило сравнения |
|---|---|---|
| `environment` | железо (CPU-модель, ядра, RAM, тип диска), kernel, `ulimit -n`, governor, версия Compose, cgroup-лимиты per service, размещение генератора, бюджетный пресет **с фактическими значениями**, профиль нагрузки, substrate и его параметры, движок и размер tenant DB, число tenant'ов, `DEMO_HISTORY_TURNS`, `BACKLOG_MODE`, хардкод-константы, которые нельзя задать env (`PROACTIVE_RECONNECT_IDLE_SECONDS=240`) | при сравнении отчётов должны совпадать полностью |
| `code` | commit SHA, digests образов, число воркеров api-service | предмет сравнения; при soak — неизменны (иначе abort) |

Плюс **quiet-host preflight** до старта: load average, CPU governor, отсутствие соседних тяжёлых
процессов, `ulimit -n`, синхронизация времени (NTP при внешнем генераторе — иначе декомпозиция
client/server поедет). **В `run_guard.py` таких проверок нет вообще** — guard умеет только O_EXCL-лок,
stale-PID cleanup и атомарный манифест, а существующий preflight (`runner.py`) проверяет лишь
доступность API/агента. Quiet-host preflight и есть расширение RunGuard из §11.

**Хост замера выбирается до фазы 1, а не по ходу.** Половина плана — предположения о Linux, и на
машине разработки (Darwin/arm64) они не выполняются: `macvlan`/IP-алиасы для `clients.source_ips > 1`
(§5), `tc netem` и SIGSTOP (§9), cgroup-сбор per service, `ulimit -n` — всё это либо отсутствует,
либо живёт внутри VM Docker Desktop и не наблюдаемо так, как описано. CI здесь не помощник:
GitHub-hosted `ubuntu-latest` — соседнее шумное железо с жёстким лимитом джобы, то есть
quiet-host preflight на нём неисполним по определению, а soak не влезает в бюджет. Значит в
`environment`-группе манифеста хост — **конкретная named машина** (Linux VM с известным CPU/RAM/диском,
права `NET_ADMIN` для netem, доступ к cgroup), и `ci-stress-smoke` (§12) с ней не пересекается: CI
проверяет схемы, но не меряет.

Зафиксировано измерением (commit `a700cba`): в проекте **нет** `uvicorn --workers` /
`WEB_CONCURRENCY` ни в compose, ни в `dev.sh` — api-service это один процесс с одним event loop.
Число воркеров пишется в манифест, потому что это первое, что изменит любой будущий фикс ёмкости.

## 7. Критерии прохождения (SLO)

| Утверждение | Критерий |
|---|---|
| Ёмкость слоя | на стадии: achieved ≥ 0.98 × target, `error ≤ 1%`, ассертится **`platform_overhead p95 ≤ T`** (дефолты: L1 50 ms, L2 500 ms, L3 500 ms) |
| Knee | следующая стадия нарушает p95 или error-критерий, knee уточнён бисекцией до ±10%; ищется **только при `budget_preset: off`** (§5) |
| Soak | 70% от knee; дрейф p95 на 24-часовых окнах ≤ +20%, абсолютные дельты и тест на **тренд** для FD/горутин (см. §8), ошибки ≤ 0.1%/ч |
| Зависание зависимости | 100% запросов получают sanitised ответ, классифицированный как retryable **по `outcome.retryable` в backlog**; после восстановления ресурсы и p95 возвращаются к baseline |
| Бюджеты | 429 ровно на превышении, `Retry-After > 0`, отказ быстрый, соседний canary не затронут |

- `T` — параметр запуска, а не константа: отчёт печатает, при каком `T` посчитан вердикт.
- **Какой перцентиль судит вердикт — определено по слоям, и L3 пока отказывается.**
  `platform_overhead p95` считается **на стадию** из фактических per-request таймингов LLM
  (`summarise(..., llm_latency_ms=...)`), а не подставляется одним числом на весь прогон: у стадий
  разная доля модели внутри хода. Там, где внутри хода модели нет (L1, L2), вердикт опирается на
  компенсированный перцентиль хода, и это записано правилом слоя в отчёте по имени, а не оставлено
  на догадку. Механизм есть (`summarise(..., llm_latency_ms=...)`), но вызывать его будет драйвер L3
  в фазе 2: сегодня `platform_overhead_p95` не заполнен ни на одной стадии, и вердикт всюду опирается
  на описанный фолбэк по слою. На L3 оверхед вычислить нечем, пока подложка не отдаёт тайминги,
  поэтому `run_ladder` **отказывается** планировать L3/L4 — забор стоит и в `LadderPlan.for_profile`,
  и в самом `run_ladder`: план, собранный руками, обходит первый забор, и тогда честные 2.5 s модели
  печатаются как провал платформы: судить L3 по времени хода значило бы выдать честные 2.5 s
  модели за провал платформы и напечатать `below_first_rung` как вердикт. Отказ — это ответ; тихий
  фолбэк на неподходящую метрику — нет.
- **Критерий ёмкости — `platform_overhead`, а не `t_complete`.** Честная латентность модели
  (p95 2.5 s) не должна валить стадию: `t_complete p95` (дефолт 3 s для L3) печатается вторичной
  колонкой и объясняется моделью. Исключение — L2, где LLM≈0: там критерием идёт и `t_complete`.
  Это работает только благодаря фазе 0 (§0): до неё вычитание было no-op.
- **Стадия невалидна, если измеренная очередь прибора заняла бюджет.** Точный вариант (после
  инструментации stub, §4): `p95(queue_wait) > 0.25 × T` → стадия невалидна. Дешёвый вариант до неё:
  расхождение per-request разниц `platform_overhead − platform_overhead_model` (не «p95 минус p95»,
  а распределение) с тем же порогом. Порог привязан к бюджету платформы, а не к константе T/2: у L1
  (T = 50 ms) и L3 (T = 500 ms) масштаб разный.
- **Warm-up не входит** ни в одну из метрик выше. Для `achieved` это значит, что знаменатель —
  `(total_ticks − warmup_ticks) / rps`, а не `duration_s − warmup_s`: тики целые, и на короткой
  стадии эти величины расходятся на тик. Раньше округление вниз в счётчике warm-up при фильтре
  `planned_ms >= warmup` давало `achieved` ниже цели даже на стадии, которая выполнила все тики по
  расписанию (D = 4 s, w = 1.5 s, 5 rps: 12/2.5 = 4.80 < 0.98 × 5), то есть §7 валил исправный
  прогон. Теперь определение warm-up одно — `ceil(w × rps)` — и из него выведены и фильтр, и
  знаменатель.
- **Error-бюджет определяется отдельно на пресет**: при `budget_preset: on` 429 не считается ошибкой
  ёмкости, но учитывается как отказ обслуживания.
- **Таксономия ошибок пишется в raw JSONL структурно** (не по тексту — текст локализован ru/en):
  - транспорт/бюджеты: `429_budget`, `timeout_client`, `timeout_server`, `5xx`, `reset`, `sse_abort`;
  - терминаторы хода: `limit_model_calls`, `limit_tool_calls`, `limit_context`
    (из `outcome` записи backlog `error`), `turn_limit` (`max_user_turns_per_session`);
  - наш собственный scheduler: `mcp_lock_timeout` (метрика фазы 0) — класс, отличающий сериализацию
    на tenant от отказа зависимости;
  - `other`.

## 8. Что именно проверяет 48-часовой soak

Долгий прогон нужен не за rps, а за монотонным дрейфом. Критерии — абсолютные дельты и наклон
тренда, а не проценты от десятков: «FD +≤1%» при счёте в десятках бессмысленно.

| Наблюдаемое | Критерий |
|---|---|
| FD, горутины (gateway/data-service), asyncio-задачи, `mcp-owner-*` | нет монотонного роста (slope ≈ 0, дельта в абсолютных числах) |
| RSS | ramp-up до плато после прогрева, затем плато; оговорка на аллокатор Python — порог задаётся на плато, не от старта |
| In-memory состояния анти-абьюза | эвикция на 4096 записей работает: размер не растёт |
| БД сессий | **retention у сессий нет**: чистятся только ходы внутри сессии (последние `DEMO_HISTORY_TURNS`), строки `sessions` и число файлов растут монотонно. Это ожидаемое поведение, а не утечка, но отчёт печатает абсолютный рост и его наклон, а `price-of-time` без него невалиден |
| Backlog | **retention-джобы нет**: `cleanup_old()` вызывается один раз при старте сервиса, дальше каталог растёт. Печатать байты/с и свободное место на volume: при `BACKLOG_MODE=full` запись идёт на каждый ход (и на каждый tool_result целиком), pretty-print с сепараторами |
| p95 по часам | нет тренда; проактивный реконнект MCP-сессий (240 s idle, хардкод) виден на графике как контролируемая пила |
| Смена суток | никакие таймеры/кулдауны не ломаются на границе суток |

**Прибор входит в нагрузку.** Запись backlog — синхронные `open`/`write`/`close` в event loop
api-service (без `to_thread`, без fsync), а `platform_overhead` **требует** `BACKLOG_MODE=full`.
Значит `full` — одновременно источник истины и фактор нагрузки, и в отчёте это отдельная строка.
Различающий прогон дешевле tmpfs-эксперимента для SQLite: тот же профиль на `BACKLOG_MODE=off`
(и, если эффект переживёт, `errors`) — тот же класс приёма, что §15 применяет к хранилищу сессий.

**Почему запись пока синхронная.** `_BacklogRecorder` назван по делу и не выдаёт себя за
асинхронный: порядок записей внутри файла сессии читает bench-парсер (он берёт первый
`turn_end` по порядку), а `test_backlog_concurrency` («HIGH-2») описывает гонку при записи
одной сессии из нескольких потоков — лока в `ModelBacklog` нет, и тест проходит по удаче
(5 прогонов подряд зелёные). Наивный переезд на `asyncio.to_thread` усилил бы именно этот
риск, поэтому неблокирующая запись — отдельная задача (single-writer task + FIFO-очередь,
сохраняющая порядок, плюс drain для харнесса), а не побочный эффект рефакторинга шва.

Soak идёт на фиксированной ревизии: изменение digest образа → автоматический abort. MVP — 12–24 часа;
48 часов запускать только после чистого короткого прогона: 48 h на непроверенном стенде =
гарантированная переделка.

## 9. Overload, DoS и инъекция отказов

Строки делятся на два класса, и разделение обязательное:

- **Assert-сценарии** (машинный критерий, это regression-контракт): превышение бюджетов (429 +
  `Retry-After` + canary не затронут), ротация `session_id`, удержание SSE без чтения, открытые
  MCP-сессии (ресурсы не растут), зависание gateway и tenant DB (sanitised ответ, retryable по
  backlog).
- **Observation pass** (без pass/fail по определению): форма деградации при 10× потолка и фаза
  восстановления. Здесь снимаются таймлайн и графики, а вывод идёт в отчёт как narrative.
  Не помечать его явно нельзя — иначе фаза 5 превратится в «погоняли, посмотрели глазами».

| Сценарий | Что проверяем |
|---|---|
| превышение бюджетов с одного IP (10× **бюджета**) | 429, `Retry-After`, быстрый отказ, canary не затронут |
| превышение 10× **найденного потолка** при `budget_preset: off` | форма деградации (растёт очередь или p95 взрывается), что умирает первым (CPU/FD/RAM), **и фаза восстановления**: возвращаются ли p95 и ресурсы к baseline, нет ли шторма реконнектов и half-open шторма circuit breaker |
| ротация `session_id` | per-IP bucket не обходится, память не растёт |
| удержание SSE без чтения (N штук) | рост памяти ограничен событиями одного хода; FD не течёт, воркеры не блокируются. **Серверного таймаута на удержание нет**: `asyncio.Queue` без границы, latch срабатывает только на реальный disconnect, поэтому «таймауты срабатывают» — неверная формулировка v3. Отдельно фиксируется, что нечитающий клиент всё равно доводит ход до конца и **тратит токены провайдера** (это уже про cost/abuse, не про ёмкость) |
| открытые MCP-сессии без закрытия | лимиты/GC (`MCP_MAX_IDLE_SECONDS=600`), рост задач, поведение при исчерпании |
| длинные `limit`, regex-паттерны, длинная история | завершение по timeout (per-query timeout data-service 30 s) либо терминатор `CONTEXT_LIMIT`; БД не блокируется насмерть |
| `mcp-gateway` завис (SIGSTOP / `tc netem` DROP), затем `down` | таймауты и circuit breaker на **hang**-пути, а не только fast-fail |
| tenant DB завис | класс ошибки retryable/sanitised, чужие tenant'ы не затронуты |
| насыщение per-tenant `call_lock` | `mcp_lock_wait_seconds` растёт, `mcp_lock_timeouts_total` начинает считать, `mcp_tool_timeouts_total` — нет: сериализация не должна выглядеть как отказ зависимости |

Два обязательных условия:

- **Canary-контроль.** Во всех abuse/overload-сценариях в фоне идёт низкотемпературный трафик
  выделенного tenant'а и IP; assert — их p95 и ошибки не изменились. Без этого «соседи не затронуты» —
  заявление без проверки.
- **`down` ≠ `hang` ≠ partition.** Fast-fail путь (контейнер упал) проверяет только отказ
  соединения; таймауты и полуоткрытый breaker живут на зависании. Инъекция — SIGSTOP / netem,
  остановка контейнера — отдельный кейс.

Каждая находка конвертируется в детерминированный regression-тест (правило репозитория: сначала
падающий тест) и в запись отчёта со ссылкой на коммит-фикс. `scripts/verify_sse_gateway_outage.sh`
переиспользуется как **источник приёмов**, не как библиотека: это самостоятельный E2E с
захардкоженными именами контейнеров (`infra-mcp-gateway-1`, `infra-data-service-1`), портом 18081 и
собственным inject/assert/cleanup.

## 10. Evidence layout, единый JSONL и отчёт

Основа — фактические артефакты бенча, а не желаемый layout:

```
test-results/stress/<run_uuid>/      # test-results/ в .gitignore
  run-manifest.json    # + environment/code split (его в бенче нет — расширение)
  preflight.json       # quiet-host + loopback-калибровка (в бенче только reachability)
  profile.json         # снимок профиля нагрузки
  raw/*.jsonl          # ЕДИНАЯ схема для всех драйверов: per-request записи
  generator/*.json     # CPU/лаг генератора, dropped ticks
  stub/*.jsonl         # тайминги заглушки на запрос: arrival/service_start/service, queue_wait
  server/*.json        # срезы /metrics по времени; пропущенный скрейп помечается gap, не нулём
  host/*.json          # cgroup CPU/RAM/IO, FD, горутины
  report.json          # машиночитаемый вердикт
  report-*.md          # таблица + knee-график + soak-тренды
```

Что здесь новое, а что унаследовано (проверено по `run_guard.py`):

- унаследовано: lock `.benchmark-locks/api-{digest}.lock`, атомарный манифест, stale-PID cleanup,
  `runs/<uuid>/` как корень артефактов;
- **новое**: разделение манифеста на `environment`/`code` (в бенче манифест плоский v1), отдельный
  `preflight.json`, статус `aborted` и `abort_reason` (**в бенче `finalize()` принимает только
  `completed|failed`, иначе `ValueError`**), `profile/report` схемы, `compare`/baseline (его нет),
  quiet-host preflight (§6), отдельный `status.json` (в бенче статус — поле манифеста).

**Сбор серверных данных — отдельный шаг, и он не бесплатный.** `/metrics` api-service закрыт API
bearer'ом (`private_router`), значит скрейп Prometheus нужен с токеном. Backlog и SQLite лежат на
volume `app_data:/data/app` (`BACKLOG_DIR=/data/app/backlog`, `DEMO_SESSION_DB_PATH=/data/app/demo_sessions.sqlite`),
то есть экспорт из контейнера (`docker cp`/`exec`) — часть пайплайна; файлового flush-API у backlog
нет, поэтому серверная правда читается после прогона.

**Первый сквозной прогон лестницы (2026-09-27, изолированный стенд, Darwin-ноутбук).** Лестница
40→80→160→320 rps, T = 50 ms, длительность 10 s, warm-up 2 s, repeats 2, один tenant:

| target rps | achieved | p50 | p95 | overhead p95 | err% | lag p99 | workers | CPU генератора | вердикт |
|---|---|---|---|---|---|---|---|---|---|
| 40 | 40 | 1.6 | 2.1 | 2.1 | 0 | 0.002 | 42 | 16% ядра | pass |
| 80 | 80 | 1.4 | 1.9 | 1.9 | 0 | 0.010 | 84 | 30% ядра | pass |
| 160 | 157 | 12.7 | 25.2 | 25.2 | 0 | 6.32 | 168 | **114% ядра** | invalid |

Knee — **80 rps как нижняя граница**, и это ровно тот случай, для которого слово «граница» и нужно:
следующая ступень не провалилась, а не измерена (генератор на том же 8-ядерном хосте, что и
сервисы). Прогноз §3 дал 1295 rps против найденных ≥80 (отношение 0.06) — расхождение здесь
объясняется не моделью сериализации, а тем, что лестница до потолка платформы просто не дошла.
Три факта, которые прогон добавил к дизайну:

- **Рукопожатие пула — это всплеск, а не фон.** Открытие 168 сессий в тесном цикле дало 600–700
  запросов за ~200 ms (`initialize` + `notifications/initialized` на сессию), то есть мгновенные
  ~3000 запросов/с, и ступень умерла на HTTP 429 **до первого тика**. Отсюда темп открытия пула
  (`SESSION_OPEN_RATE = 100` сессий/с, `stress/runner.py`): пауза идёт до старта часов стадии и
  внутрь измерения не попадает. Любой, кто поднимает пул в цикле, обязан это учитывать.
- **Исчерпание портов — тоже потолок прибора.** При 480 rps (504 сессии) прогон упал с
  `OSError: Can't assign requested address`; на 320 rps тот же прогон проходит. Ширина пула
  ограничена не только CPU, но и эфемерными портами и `ulimit -n` (§6).
- **Гейтвей резолвит конфиг тенанта на каждый MCP-запрос.** По логу: «Fetching config for tenant» —
  319 раз на 319 входящих запросов в секунду. То есть каждый tool call на L1 это gateway → HTTP в
  data-service за конфигом → сборка registry → tool → снова data-service → БД, и knee L1 упирается
  в этот путь, а не в query engine. Продуктовое наблюдение, не правка харнесса: измерено, записано,
  решение о кеше конфига — отдельный разговор (в дизайне это причина, по которой L1-число нельзя
  пересказывать как «потолок БД»).

**Единая схема raw-JSONL — главное требование к архитектуре измерений.** L1–L3 гоняются разными
драйверами, и если перцентили считать «где получилось», слои окажутся яблоками и апельсинами.
Поэтому: любой драйвер пишет одну и ту же per-request запись
(`planned_ms`, `actual_ms`, `ttfe_session`, `ttfe`, `ttfe_tool`, `t_complete`, `prompt_tokens`,
`history_turns` (план), `session_id`, `tenant`, `scenario`, `status`, `http_status`,
`sse_terminal_event`, `error_class`, `terminator`), а **все перцентили, включая CO-компенсацию,
считает один Python-калькулятор**; агрегаты внешних инструментов — только справочная колонка.
Плюс к этому списку — `started_ms` (смещение фактического старта): без него калькулятор не знает,
от какого старта измерен `actual_ms`, и компенсация молча расходится между драйверами (обоснование —
в докстринге `stress/records.py`). Единица записи — то, что планирует генератор: для L1 это **ход**
(запись на вызов размножила бы CO-компенсацию и разошлась бы с §3), а подекомпозиция по вызовам
пишется рядом отдельным файлом `raw/<stage>.calls.jsonl` с таймингами без собственных плановых
смещений.
Бюджеты в манифест берутся **из окружения сервисов, а не харнесса** (`collect_budgets(..., overrides=...)`):
на стенде лимитер поднят, а харнесс запущен снаружи, и «дефолт по документации» рядом с поднятым
лимитером — это ровно та ошибка, от которой §5 предупреждает. Значение, которого в окружении
сервисов нет, описывается явно, включая «отсутствует на этом стенде».

Вердикт стадии считается по **компенсированному** p95 и включает достигнутый темп (`achieved ≥
0.98 × target`): без компенсации открытый контур занижает перцентили, а без проверки темпа ступень,
прогнавшая меньше ходов, чем просили, выглядела бы доказательством удержанной скорости.

Если ступень выше knee невалидна, отчёт обязан называть knee **нижней границей**: платформа не была
уличена в провале на следующей скорости, и напечатать это как потолок значило бы выдать knee
прибора за knee платформы.

Джойн серверной правды: (файл сессии → `session_id`, `turn_id`) для записей `llm_call` / `tool_result`
/ `error`; после фазы 0 `session_id` есть и в самой записи `llm_call`.

**Лаг event loop генератора — first-class метрика, а не деталь.** CPU у asyncio-драйвера может
показывать 30% при забитом event loop, поэтому в отчёт идёт histogram лага с assert `p99 < 5 ms`:
нарушение инвалидирует стадию так же, как dropped ticks. **Authority по метрикам фиксируется в
отчёте:** `ttfe`/`ttfe_tool` считает Python-драйвер; k6-расширение отдаёт события по мере прихода,
поэтому first-event latency вычислима и служит перекрёстной проверкой, но доверие к ней включается
только после сверки в фазе 2, и у каждой метрики в отчёте указан драйвер-источник.

**Драйвер собран на потоках, а не на event loop, и свой лаг пришлось лечить (измерено 2026-09-27,
Darwin-ноутбук, стенд из двух нативных сервисов).** При 50 rps на 8 и 32 воркерах обычный `sleep`
даёт лаг p50 ≈ 10.0 ms и p99 ≈ 10.03 ms — одинаково на обеих ширинах пула при CPU генератора 2%.
То есть это не насыщение планировщика, а квантование таймера хоста: каждая стадия была бы
невалидной по причине, не имеющей отношения к SUT. Угаданный хвост busy-wait не спасает: 1 ms
оставляет пол в 4 ms, а фиксированные 10 ms съедают 30% ядра на 50 rps. Поэтому хвост
**калибруется**: раннер измеряет запаздывание пробуждения на той длительности, с которой реально
спит воркер (`interval × workers`), и держит спин-только этот хвост. На том же 50 rps: лаг p99
0.009–0.010 ms, максимум 0.14 ms, стадия валидна, цена 16–17% одного ядра. Факт: промах `sleep`
зависит от запрошенной длительности (проба 5 ms на этом хосте врёт в два раза), поэтому
калиброваться надо на своей длительности. Использованный хвост — поле результата стадии, а не
скрытая константа в коде: он печатается рядом с CPU генератора, потому что это часть описания
прибора. Провал лага уходит в `invalid_reasons()`, а не в вердикт.

Контракт отчёта (колонки фиксированы, чтобы прогоны сравнивались глазами, а не пересказом):
`profile | scope (separate|composite) | target rps | achieved | p50 | p95 | p99 | err% |
platform_overhead p95 | platform_overhead_model p95 | stub queue_wait p95 | mcp_lock_wait p95 |
prompt_tokens p50 | terminator mix | SUT CPU | generator CPU | lag p99 | verdict |
environment hash` + knee-график (rps → p95) + строка «предсказано / найдено» (§3) + soak-тренды.
Колонка `generator CPU` считается от всей стадии (тот же знаменатель, что у гейта насыщения).
Три колонки-расширения к списку — `pool expansions | dropped ticks | spin tail ms`: без них rung,
удержанный на номинальной ширине пула, неотличим от rung, которому понадобилось расширение, а
«невалидная стадия — это действие» (§2) не оставляет следа в артефакте. Каждая попытка и каждый
повтор несут **билет** (`StageTicket`: rps, номер попытки, номер прогона), поэтому сырые записи
раскладываются по файлам вида `raw/<rps>-run<k>-attempt<n>.jsonl`: без билета повторные прогоны knee,
из которых считается headline, смешивались бы в один файл, и медиана §2 не воспроизводилась бы из
«канонического источника перцентилей». Пустые ячейки печатаются
как `n/a` **с причиной** в отдельной секции: пустая ячейка — тоже утверждение, и оно должно быть
объяснено.

Отчёт обязан говорить, **сколько прогонов knee реально усреднено**: `headline.runs` — валидные
прогоны, `runs_requested` — заказанные, `runs_discarded` — выпавшие невалидными. Медиана считается
по тому же перцентилю, которым судили вердикт (иначе рядом оказываются две разные метрики одного
прогона), а повторные прогоны knee идут через тот же приёмник сырых записей, что и ступени, — иначе
«канонический источник перцентилей» не содержит записей, из которых посчитан headline. Если knee
стоит на верхней ступени лестницы (все ступени прошли) или ступень выше него невалидна, отчёт
обязан называть knee **нижней границей**: ни один прогон не показал провала выше неё. Каждая
попытка ступени попадает в приёмник (включая отброшенную из-за расширения пула), иначе «сколько
воркеров понадобилось» теряется вместе с отброшенным прогоном.

синтетическими tenant'ами на тест-профиле.

## 12. Anti-rot: почему харнесс не развалится при обновлениях

1. **CI-смоук** (≤90 s; таргет `make ci-stress-smoke` появляется вместе с фазой 1 — сейчас его
   нет ни в `Makefile`, ни в CI, и ссылаться на него как на существующий нельзя): test-профиль,
   L0+L1 на 5 rps, проверка `achieved ≈ target`, рендер отчёта, валидация схем
   `profile.json`/`report.json`, запись манифеста. **Без порогов производительности** — иначе CI
   станет флаки. CI проверяет схемы, но ничего не измеряет: стенд для чисел — отдельная машина
   (§6).
2. **Contract-тесты — это новая работа, а не существующая.** Их нет ни для профиля, ни для отчёта,
   ни для JSONL, ни для backlog; ни теста «имена тулов ⊆ манифест», ни теста соответствия заглушки
   OpenAI-контракту. Требуемый набор:
   - схема профиля и отчёта, схема raw-JSONL;
   - stub соответствует OpenAI-контракту, который ждёт LiteLLM;
   - имена тулов в профиле и в scripted-JSONL ⊆ `/mcp/manifest` (иначе явный отказ);
   - **схема backlog** (`llm_call`/`turn_end`): `duration_ms > 0`, наличие `session_id` и `turn_id`,
     поля `outcome`/`retryable` в записи `error`. Это не абстрактное требование: `duration_ms` уже
     был молча сломан (см. §0), и падение было поймано только ручной верификацией;
   - RunGuard (8 тестов есть, **но `tests/test_bench_core.py` не подключён ни к `ci-test-py`, ни к
     CI** — это отдельный пробел репозитория, который стоит закрыть).
3. **Baseline-сравнение** — не в CI, а по расписанию: `compare` против сохранённого baseline при
   совпадении `environment`-группы манифеста; деградация > N% → fail со ссылкой на diff
   `code`-группы. Механизма сейчас нет — это новая работа фазы 7.

## 15. Что этими числами утверждать нельзя

- «N rps в продакшене» — только «N rps на одном узле, при таком профиле, такой БД и такой
  латентности модели».
- Горизонтальное масштабирование не проверено: один узел, один процесс api-service, SQLite для
  сессий. Прогон на N реплик — другая гипотеза (и там ломаются process-local сессии, stateful
  MCP-хендлеры gateway и пул провайдеров), вне рамок этого дизайна.
- **Известные переменные, влияющие на tenant-fanout** (по убыванию цены различающего прогона):
  1. сессии и агенты живут в общих SQLite-файлах (`DEMO_SESSION_DB_PATH`, `agents.sqlite`), tenant в
     хранилище сессий не участвует — все tenant'ы делят один файл и один `threading.RLock` процесса;
     `agents.sqlite` добавляет второй файл и второй глобальный лок на каждую операцию, включая
     чтения. Различающий прогон: `DEMO_SESSION_DB_PATH` на tmpfs (переменная уже есть);
  2. прибор: `BACKLOG_MODE=full` обязателен для `platform_overhead`, а запись backlog синхронна в
     event loop. Различающий прогон: `BACKLOG_MODE=off|errors` (§8);
  3. spending: глобальный лок и полная перезапись `.data/spending.json` на каждый model call.
  Вывод «деградация в X раз из-за сериализации на tenant» валиден только после 1–2; иначе причин
  придётся называть три.
- **Числа не переносятся между хостами.** `quiet-host preflight`, `tc netem`, multi-IP и
  cgroup-сбор требуют named Linux-стенда (§6); GitHub-раннер и машина разработки (Darwin/arm64)
  ими не являются.
- Числа stub-прогонов ничего не говорят о качестве ответов; бенч ничего не говорит о ёмкости.
- Soak на dev-железе не заменяет прод-наблюдаемость: retention, бэкапы и деплой под нагрузкой
  остаются вне рамок. Отдельно: у хранилища сессий retention нет вообще, а backlog чистится один раз
  при старте, поэтому «рост объясним» — не то же самое, что «рост ограничен».
- `price-of-time` со старением системы описывает поведение конкретной продолжительности прогона,
  а не установившийся режим.
- Prometheus у api-service не является независимым источником LLM-латентности «из коробки»:
  `llm_duration_ms` и родственные метрики были объявлены и мертвы; после фазы 0 они живые, но это
  **тот же** замер, что и в backlog, — перекрёстная проверка, а не второй прибор.

## 16. Зафиксированные решения

1. **Где живёт:** `agent_db/stress` в agent-db + `infra/` для k6 и stress-профиля. Отдельный
   сервис не создаётся.
2. **Инструменты:** Python-asyncio-драйвер обязателен (CI-смоук, L1, любой слой). k6 — **не
   решено**: кандидат на headline-прогоны через community-SSE-extension вне CI, но выбор делается
   в фазе 2 по измеренному лагу event loop Python-драйвера (§11), а не заранее.
3. **Soak:** MVP 12–24 h, затем 48 h; ручной старт, quiet-host preflight, авто-аборт по дрейфу и
   по изменению digest образа.
4. **`remote-free` исключён**, `local` модель закрывает «реалистичную» точку (требует поднять Ollama
   отдельно — в compose её нет).
5. **Discoverability:** `doc/stress/` зарегистрирован в каталоге `AGENTS.md` (маршрут «нагрузка,
   ёмкость, stress/soak» + строка группы), иначе документ умрёт ровно так, как §12 обещает не дать
   ему умереть. Ячейка маршрута помечена как «дизайн; харнесс не реализован», чтобы приход по
   маршруту не читался как «здесь работает инструмент».
6. **Хост замера — named Linux-машина**, выбирается до фазы 1 (§6); CI (`ubuntu-latest`) проверяет
   схемы и стендом не является.
7. **Фаза 0 сделана и является предусловием:** без измеренного `duration_ms` `platform_overhead`
   невычислим, а knee-вердикт вырождается в `t_complete` (§0, §1).
8. **Профиль не упирается в серверные лимиты хода** (`AGENT_MAX_TOOL_CALLS=10`,
   `AGENT_MAX_TURN_TOKENS=8000`) и не считает объявленную историю фактической: отчёт печатает
   `prompt_tokens` и распределение терминаторов (§3).
