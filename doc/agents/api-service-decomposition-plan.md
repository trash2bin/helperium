# api-service: план декомпоновки, снятия потолка и валидации

> Статус: идёт. Написано по замерам 2026-10-03; обновлено 2026-10-04 по результатам
> Трека 0, диагностики зомби-ходов и Трека 3 (multi-worker + Redis). Прогресс и числа —
> `doc/stress/RUN-2026-10-04-l2-darwin.md`. Коммит — только по явной просьбе.

## 0.5 Переопределение bottleneck (2026-10-04, по замеру)

Гипотеза «потолок = одно ядро × per-call овеерхед litellm» подтвердилась лишь частично.
Замер на 4 воркерах показал: два процесса сидят на 98% CPU, два простаивают (0 соединений).
То есть упираемся в CPU, но не в «одно ядро», а в **неравномерное распределение долгих
SSE-соединений по воркерам** (SO_REUSEPORT не переезжает установленные соединения). Это
артефакт стенда без обратного прокси: haproxy `leastconn` выровнял соединения и поднял knee
28→31. Главный bottleneck остаётся прежним — LLM-клиентская обёртка (~55% CPU на вызов),
она режет потолок насыщенных воркеров, и Трек 2 (обход litellm) в силе. Но измерять его
эффект на Mac нельзя (троттлинг, E-ядра) — нужен Linux-стенд §6 RUNBOOK. Полный разбор —
`doc/stress/RUN-2026-10-04-l2-darwin.md`.

## 0. Зачем: проблема, измеренная, а не предположенная

Нативный Mac-стенд (data-service 8084, mcp-gateway 8083, api-service 8081, стаб LLM
9099, SQLite `sqlite-testseed`, 8 ядер, хост простаивал load ~2.7).

| Слой | Диапазон | Бюджет | Knee | Что именно ломается |
|---|---|---|---|---|
| **L1** (MCP → gateway → data-service, без LLM) | 5→1280 rps | 50 мс | **80 rps** | нижняя граница: 80 rps проходит p95 1.2 мс / 0% err; 160 rps невалидна по **генератору** (90.8% CPU прибора, 310 дропов), не по серверу |
| **L2** (chat через api-service, стаб ~0 мс) | 5→80 rps | 500 мс | **20 rps** | 20 rps p95 105 мс / 0% err; 40 rps invalid (p95 3522/6815/10375 мс, **104 `sse_abort`**, 708 дропов) |

**Главный факт:** на L1 те же тулы через прямой MCP идут 80+ rps почти без нагрузки
(Go-сервисы простаивают), а тот же ход через api-service на L2 упирается в ~20 rps.
**Разница — это api-service, не платформа.**

### 0.1 Куда именно уходит CPU (py-spy `--gil`, 40 rps L2)

| Что ест GIL | Доля | Это наш код? |
|---|---|---|
| litellm `acompletion` | 32% | ❌ нет (зависимость) |
| openai SDK `_async_transform_recursive` | 14.6% | ❌ нет (зависимость) |
| typing `get_origin` | 3.4% | ❌ нет |
| json `iterencode` | 2.1% | ❌ нет |
| httpx pool | 2.4% | ❌ нет |
| наш MCP-клиент | 0.7% | ✅ да |

≈ **55–60% ядра — это litellm + openai SDK**, то есть per-call овеерхед LLM-клиента, а
не бизнес-логика. Замерено напрямую: один `acompletion` с 3 инструментами = **2.59 мс
CPU** (без инструментов 1.17 мс). При 20 rps × 3 вызова = 60 вызовов/с × 2.59 мс =
**15.5% ядра только на litellm**; при 40 rps — 31%.

**Вывод: потолок — это «один процесс api-service × per-call овеерхед», а не «Python
вообще».** Своя оркестрация почти не ест CPU (0.7%). Поэтому смена стека сейчас даст
мало; снятие овеерхеда и распараллеливание — много.

### 0.2 Отдельная болезнь: деградация не лечится (hysteresis)

Повтор knee (20 rps) **после** стадии 40 rps дал p95 **1328 мс** (fail) вместо 105 мс
(pass). Медленным был **с первого хода** (`started_ms=50` → 671 мс), то есть система не
восстановилась после 40 rps. Распределение: p50 43.9 мс (норма), p95 1209 мс, 399 из
1800 ходов > 500 мс, max 2408 мс. Тормозит **первое событие SSE** (`ttfe_session` ≈ 10 с
при перегрузе) — ход висит на старте, ещё до работы модели.

Подтверждение механики: `sse_abort: 104` при `ttfe_session ≈ t_complete ≈ 10 с`. Причина,
по которой проверяем — **клиент отвалился, сервер продолжает**: `disconnect_check`
проверяется **только перед вызовом модели** (`loop.py:235`), а не между вызовами тулов и
не на каждой итерации. Оборванные ходы продолжают жрать CPU → раскручивают перегруз.

### 0.3 Мы вслепую: `/metrics` api-service отдаёт 403

Все 132 скрейпа api-service → gap (`HTTP 403`). У data-service 132 скрейпа / 0 gap. То
есть CPU api-service и `mcp_lock_wait_p95` в числах прогона **отсутствуют** — пока
метрики не починены, любое «до/после» по серверу считаем по py-spy и raw-записям, а не
по /metrics.

### 0.4 Оговорка про «потолок платформы»

Мы измерили **колено api-service = 20 rps**. Мы **не** измерили, сколько может вся
платформа: на L1 потолком стал генератор (90.8% CPU прибора), а не gateway/data-service.
До снятия потолка генератора верхняя планка платформы неизвестна, и любое решение о
стеке — гадание. Это первый трек плана.

## 1. Цель: чего хотим добиться

**Одна строка:** поднять сквозной колено L2 как минимум в 2 раза (20 → ≥40 rps) и
устранить hysteresis, чтобы повтор knee воспроизводился, а не рос после высокой стадии.

Конкретные, проверяемые цели:

| # | Цель | Сейчас | Целевое | Как меряем |
|---|---|---|---|---|
| G1 | **L2 knee** | 20 rps | **≥ 40 rps** (амбициозно 80) | `agent-db-stress run chat-zero-latency-l2`, статус `knee_found`, число |
| G2 | **Hysteresis** | повтор knee = 1328 мс (fail) | повтор knee ≈ первый замер (±20%), **0% err** | два прогона knee подряд, p95 повтора ≈ p95 первого |
| G3 | **Зомби-ходы** | оборванный ход жрёт CPU дальше | ход прерывается ≤1 итерации после disconnect | `sse_abort`/`ttfe_session` в raw + py-spy во время стадии 40 rps |
| G4 | **Multi-worker** | 1 процесс, 1 ядро | N процессов × ядра, корректный rate limit | L2 knee с `--workers N`, knee растёт ~пропорционально N |
| G5 | **Метрики** | `/metrics` api 403 | 200, CPU + `mcp_lock` в отчёте | скрейпы без gap |
| G6 | **Потолок платформы** | неизвестен | **измерен** (L1 без потолка прибора) | L1 с разгруженным генератором, knee перестаёт быть нижней границей |

**Чего НЕ хотим:** не хотим сейчас переписывать api-service на другой язык. Профиль
показывает, что своя логика почти не ест CPU — сначала снимаем овеерхед и
распараллеливаем; смена стека рассматривается только после того, как потолок останется
и после этих шагов, и только по измеренному профилю.

## 2. Как валидируем (главное)

Валидация = **стресс-тест до и после, цифры в таблицу**. Не «стало лучше на глаз», а
одинаковые прогоны, одинаковый стенд, одинаковый профиль, разные числа.

### 2.1 Единый протокол замера (повторяется для каждого трека)

Команды (Mac-стенд уже поднят через `/tmp/start-stand.sh`):

```bash
# L1 (потолок платформы / gateway+data)
/tmp/run-l1.sh              # rates 5,10,20,40,80, t-budget 50ms
/tmp/run-l1-high.sh         # rates 80,160,320,640,1280 — ищем настоящий потолок

# L2 (потолок api-service) — главный метрик
/tmp/run-l2.sh              # rates 5,10,20,40,80, t-budget 500ms, repeats=2
```

Что фиксируем из каждого прогона (из `report-*.md` и `raw/*.jsonl`):

1. **knee rps** и статус (`knee_found` / `below_first_rung` / `invalid`).
2. **p95/p99 на knee**, err%, gen CPU %, lag p99.
3. **Hysteresis-проба:** p95 первого knee-замера vs p95 повтора (цель G2).
4. **`sse_abort` count** и `ttfe_session` по raw-записям (цель G3).
5. **`gen CPU %`** — чтобы отличить knee платформы от knee прибора (инвалидность стадии
   = генератор сел на ядро; это не потолок сервиса).

Серверная кросс-сверка (после фикса G5): `server/<service>.json`, CPU по процессам,
`mcp_lock_wait_p95`.

### 2.2 Базовая линия (зафиксировано 2026-10-03, до работ)

```
L2 knee      = 20 rps   (p95 105 мс, 0% err)
L2 repeat    = 1328 мс  (fail)  ← hysteresis
L2 40 rps    = invalid  (sse_abort 104, 708 дропов)
L1 knee      = 80 rps   (p95 1.2 мс, нижняя граница; 160 rps = генератор)
litellm/call = 2.59 мс CPU (3 tools) / 1.17 мс (без tools)
GIL split    = litellm 32% + openai SDK 14.6% + typing/json/httpx ~8% ; наш код 0.7%
```

### 2.3 Критерий «прогон засчитан»

- Лестница дошла до knee, статус `knee_found`, gen CPU на knee-стадии **< 80%** (иначе
  knee — knee прибора, и прогон нужно повторить с разгруженным генератором).
- `repeats ≥ 2` для headline (по §2 харнесса: медиана, а не единичный замер).
- raw-записи на месте, чтобы перцентили пересчитались сторонним кодом (не доверяем
  отчёту на слово).

### 2.4 Пороги решений

- Цель G1 достигнута: L2 knee ≥ 40 rps на **двух независимых** прогонах.
- G2 достигнута: |p95(повтор) − p95(первый)| / p95(первый) ≤ 0.2.
- Если после всех треков knee остаётся ниже цели и в профиле снова litellm/openai SDK
  доминируют — это сигнал, что нужен Путь 1 (абстракция/обход LLM-клиента) или Путь 4
  (смена стека), а не further tuning.

## 3. Работы: 4 трека

Порядок — по убыванию «польза / стоимость». Треки 1–3 независимы и могут идти параллельно;
Трек 0 блокирует только финальную интерпретацию потолка, но не сами работы.

### Трек 0 — измерить потолок платформы (блокирует интерпретацию)

**Почему:** сейчас «20 rps» — это колено api-service, а не платформы; на L1 потолком стал
генератор. Без верхней планки платформы мы не знаем, сколько теряем и стоит ли трогать
стек.

**Как:**
- Разгрузить генератор L1: несколько процессов-генераторов на разные ядра (или отдельная
  машина), чтобы `gen CPU %` на стадии 160/320/640 rps был < 80%.
- Прогнать L1 до реального knee перестаёт быть `knee_found` на нижней границе.
- Починить `/metrics` api-service (403): `/metrics` fail-closed за bearer`ом `/admin/*`
  (pentest M1) — убедиться, что харнесс шлёт тот же токен, что и `/admin`, либо
  объявить отдельный read-only metrics bearer. Это цель G5, её можно сделать здесь же.

**Приёмка:** L1 report без пометки «knee is a LOWER BOUND»; `server/api-service.json`
содержит series, а не gap.

### Трек 1 — зомби-ходы: проверять disconnect на каждой итерации

**Почему (п.0.2):** клиент отвалился, сервер продолжает. `disconnect_check` проверяется
только перед вызовом модели (`loop.py:235`). Оборванный ход дожигает оставшиеся вызовы
тулов и следующий раунд модели → CPU впустую → раскручивает перегруз.

**Что меняем (маленький дифф):**
1. **В `loop.run()` (`while True`, перед каждой итерацией):** текущая проверка на
   `loop.py:235` стоит перед вызовом модели — это уже правильно, но её нужно держать как
   **первую** операцию итерации (сейчас после `run.metrics.model_calls += 1` и
   логирования; проверка не должна стоить ни одного лишнего await).
2. **В `_run_tool_calls` (`for call in calls`):** добавить проверку **перед каждым
   `call_tool`** — сейчас между туловыми вызовами проверки нет вообще. Если клиент ушёл —
   прервать цикл тулов с `LoopOutcome(kind="cancelled", message=REQUEST_CANCELLED)`.
3. **После возврата `response` из `_provider.complete`:** если ход стал длинным (например,
   8 тулов в сценарии `search_get`), а клиент отвалился за это время — не запускать
   оставшиеся тулы. Проверка перед `call_tool` это покрывает.

`disconnect_check` — это нулевой-аргументный callable (`watcher.check`), уже проброшен в
`_mcp.disconnect_check` (`mcp_client.py:1563`). Внутри `call_tool` есть проверки
`client_gone` (`mcp_client.py:1314`, `:1392`) — то есть на уровне одной сессии это
частично есть; **дыра — между вызовами в `_run_tool_calls`** и в итерации цикла.

**Важно не сломать:** проверка `disconnect_check` — это отмена для читателя, а не отказ
платформы. Не должно меняться: `disconnect_check` не является поводом для
`_mark_failure`/reconnect (это пир-независимая отмена, а не смерть транспорта — см.
коммит `34bf624`). Outcome `cancelled` не должен уходить в retry/backoff.

**Приёмка (G2/G3):**
- Юнит-тест: 2 итерации цикла, disconnect ставится после первой → второй не вызывает
  `_provider.complete` (счётчик вызовов подменного провайдера = 1). Ещё тест: disconnect
  ставится между туловыми вызовами → оставшиеся тулы не вызываются.
- Стенд: стадия 40 rps после фикса — `sse_abort` остаётся (клиент реально уходит), но
  **`ttfe_session` падает с ~10 с до уровня нормы**, `gen CPU %` на следующей стадии не
  вырастает, hysteresis-проба проходит (G2).

### Трек 2 — абстракция LLM-провайдера: снять litellm с горячего пути

**Почему (п.0.1):** 55–60% GIL — per-call овеерхед litellm + openai SDK. Лителлм там не
«зря»: она даёт мультипровайдерность (единый интерфейс openai/anthropic/ollama/...),
retry/fallback и `provider_priority`. Выкинуть её целиком нельзя. Но на горячем пути
(стаб, локальный/совместимый OpenAI-endpoint) её стоимость не оправдана.

**Что меняем:**
1. **Интерфейс `BaseLLMProvider` уже есть** (`LiteLLMProvider(BaseLLMProvider)`) —
   абстракция на уровне интерфейса есть, но физически всегда создаётся `litellm.acompletion`.
2. **Добавить провайдер-реализацию напрямую на httpx:** `OpenAICompatibleProvider` —
   прямой POST `/v1/chat/completions` + минимальный разбор SSE/tools, без litellm.
   Применяется, когда `api_base` — локальный/совместимый endpoint (стаб, ollama, vLLM).
3. **Выбор провайдера по конфигурации агента:** если `provider: openai` и `api_base`
   указывает на внутренний endpoint — `OpenAICompatibleProvider`; иначе — `litellm`
   (облака, где нужны fallback/retries/priority). Селекция структурная (по конфигурации
   schema), не по тексту запроса.
4. **Кэшировать сериализованную схему инструментов:** `tools[]` JSON строится на каждый
   вызов; сериализовать один раз на сессию/аджента (в `OpenAICompatibleProvider` это
   критично, в litellm частично решается кэшем).

**Важно не сломать (контракты из AGENTS.md):**
- **No prompt steering:** поведение контролируется структурой (schemas, allow-list,
  validation, лимиты), не текстовыми уговорами. Новый провайдер не добавляет
  model-facing steering-нотисы. Существующие repair-нотисы — не прецедент.
- Санитизация ошибок: транспортные/dependency ошибки retryable и без DSN/credentials/
  путей/stack/internal hosts в публичном ответе. Это обязан держать и новый провайдер.
- `provider_priority`, retries и fallback остаются для litellm-ветки; для
  `OpenAICompatibleProvider` — тот же контракт ошибок (`CompletionResponse` с
  error-классом), но проще.

**Приёмка (G1 частично, и главный эффект на CPU):**
- **Профиль py-spy во время стадии 40 rps L2:** `acompletion`/`_async_transform_recursive`
  уходят из топа; доля litellm-оверхеда падает с ~55% до < 10%. Это и есть цель — не
  «код красивее», а **GIL перестаёт быть занят LLM-клиентом**.
- **Юнит-тесты:** провайдер отдаёт корректный `CompletionResponse` на ответ со tools;
  на 4xx/5xx возвращает тот же error-класс, что и litellm-ветка (регресс на
  контракт ошибок); схема инструментов кэшируется (один вызов построения на N вызовов
  модели).
- **Стенд:** L2 knee растёт; при 40+ rps p95 падает до сотен мс; ошибок 0%.

**Статус (2026-10-04): код готов, замер не прогнан.** `OpenAICompatibleProvider`
реализован (`providers/openai_compatible.py`), фабрика выбирает транспорт через
`LLM_PROVIDER_TRANSPORT=direct|litellm` (дефолт `litellm`, откат без revert), HTTP-ошибки
поднимаются в `ThrottledHTTPError`/`TransientHTTPError` внутри `completion_attempt`, чтобы
общий `CompletionRetryExecutor` решал retry. 8 тестов провайдера + 3 теста выбора
транспорта в фабрике; полный api-service набор 855 passed / 1 skipped. Живой замер L2
с `LLM_PROVIDER_TRANSPORT=direct` не прогонялся — вклад в knee не измерен.

### Трек 3 — вынести состояние из процесса + multi-worker

**Почему:** «одно ядро» — это не свойство Python, а один процесс. Ядер 8. Блокирует
`uvicorn --workers N` per-process состояние.

**Что именно персистентно/процессное (проверено по коду):**

| Что | Где | Тип | Готово к shared? |
|---|---|---|---|
| Session history + abuse-state | `session_repository.py` → **SQLite WAL** (`demo_sessions.sqlite`) | файл | ✅ уже файл, WAL; нужен multi-process доступ (сейчас соединение per-process?) |
| Agent store | `deps.py` → `agents.sqlite` | файл | ✅ файл |
| Rate limit | `server/rate_limit.py` `Limiter(key_func=get_client_ip)` — slowapi **in-memory** storage | процесс | ❌ нужен shared backend |
| Abuse token buckets | `anti_abuse.py` `TokenBucket`, LRU 4096, in-process | процесс | ❌ нужен shared backend (или accept-расхождение) |
| Recent messages | `RECENT_MESSAGES_*`, in-process | процесс | ❌ |
| Provider pool | `deps.py` `_provider_pool` синглтон (`global`) | процесс | ✅ по природе stateless-pool; пересоздаётся на каждый воркер |
| MCP client/session cache | `mcp_client.py` per-session proxies | процесс | ✅ per-session, воркер не зависит от соседа |
| Backlog | `BACKLOG_MODE=off` в стенде | процесс | ✅ выключен в проде; если включён — файл с локом |

**Что меняем:**
1. **Сделать SQLite shared-хранилищем для rate limit и abuse buckets.** Уже есть
   `session_repository` с `PRAGMA journal_mode = WAL` и атомарным
   `INSERT ... ON CONFLICT ... DO UPDATE` (см. `accepted_user_turn`) — тот же паттерн для
   `TokenBucket` (`INSERT ... ON CONFLICT DO UPDATE SET tokens = tokens - ?`) и для
   slowapi (кэш-таблица с атомарным списанием). Это снимает in-process состояние **без
   Redis**. Redis нужен только если SQLite покажет contention (см. риски).
2. **Убедиться, что session/agent SQLite-соединения допускают несколько процессов** (WAL
   + отдельный connection per воркер/поток; проверить busy_timeout).
3. **Поднять `uvicorn --workers N`** (N = ядер или ядра−1 на генератор). Пер-процессные
   синглтоны (`_agent`, `_provider_pool`) пересоздаются на каждом воркере — это ОК, они
   stateless; проверить, что `_sync_pool_from_store` не гоняется в гонке на старте.
4. **Проверить честность лимитов при N воркерах:** §5 RUNBOOK — лимитер обязан быть
   согласован с `--budget`, иначе §5 даёт ложный потолок. При shared-лово limiter'е
   суммарный лимит = общий, а не N×.

**Важно не сломать (контракты из AGENTS.md):**
- **Rate limit должен остаться честным:** общий лимит на N воркерах — тот же, что на 1.
  Иначе стресс даст «xN» не за счёт платформы, а за счёт N-кратного лимита (ложный
  потолок). Это проверяется в валидации (см. §2 и `--budget`).
- **Direct chat scope** — server-configured, не browser-derived; не зависит от воркера.
- **CORS / origins / auth** — из env, одинаковы на всех воркерах.

**Приёмка (G1/G4):**
- Стенд с `--workers N` (например 4): L2 knee растёт ~пропорционально (20 → 40–60 rps),
  **p95 и err% на knee остаются в бюджете**, `gen CPU %` не взлетает.
- **Проверка на ложный потолок:** суммарный `CHAT_RATE_LIMIT`/`MCP_RATE_LIMIT_RPS` при N
  воркерах не должен вырасти в N раз (иначе это не платформа, а лимит). Сверить фактический
  rate limit с `--budget` в отчёте.
- Rate limit/abuse при N воркерах: счётчики сходятся (не «каждый воркер думает, что он
  первый»).

## 4. Порядок работ и критерии приёмки (сводка)

| Шаг | Трек | Что | Критерий приёмки (цифра из §2) |
|---|---|---|---|
| 1 | 0 | Разгрузить генератор L1, померить потолок платформы; починить `/metrics` api (403) | L1 report без «LOWER BOUND»; `server/api-service.json` без gap (G5, G6) |
| 2 | 1 | Зомби-ходы: disconnect_check на каждой итерации + перед каждым `call_tool` | юнит-тесты прерывания; hysteresis-проба проходит (G2); `ttfe_session` падает (G3) |
| 3 | 2 | `OpenAICompatibleProvider` на httpx + выбор по конфигу; кэш схемы тулов | py-spy: litellm-оверхед < 10% GIL; L2 knee растёт (G1) |
| 4 | 3 | Shared SQLite для rate limit/abuse; `--workers N` | L2 knee ×N (G4) **без** роста суммарного лимита (ложный потолок исключён) |
| 5 | — | Сводный прогон L1+L2+L3 на финальном коде, повтор knee ×2 | L2 knee ≥ 40 rps, hysteresis ≤ 20%, gen CPU < 80% на knee (G1, G2) |

Каждый трек — отдельный коммит/ветка со своим regression-тестом (по правилу «при нахождении
бага — сначала test, потом код; тест обязан падать»). Валидация на стенде — после каждого
трека, не только в конце.

## 5. Риски и чего не делать

- **Не выкидывать litellm целиком:** она держит мультипровайдерность, retries,
  `provider_priority`. Новый провайдер — это **fast path**, а не замена облакам.
- **Не получить xN «за счёт лимитов»:** при `--workers N` суммарный rate limit должен
  остаться прежним. Иначе цифры лестницы — ложный потолок (§5 RUNBOOK). Обязательная
  сверка `--budget` vs фактический лимит.
- **SQLite contention:** если shared rate limit/abuse на SQLite покажет `SQLITE_BUSY` при
  N воркерах — это сигнал взять Redis для лимитов (не для сессий). Держать `busy_timeout`
  и не держать транзакции дольше одного списания.
- **Не ломать санитизацию ошибок** в новом провайдере: никаких DSN/credentials/путей/
  stack/internal hosts в публичном ответе; транспортные ошибки retryable.
- **Не добавлять prompt steering** ни в новый провайдер, ни в исправления зомби-ходов.
- **Корректность knee vs прибора:** каждая невалидная стадия с `gen CPU ≥ 80%` — это knee
  генератора, а не платформы. Не выдавать её за потолок сервиса (уже ловили на L1).
- **Смена стека (Go/Rust) — не сейчас:** профиль показывает, что своя логика почти не ест
  CPU. Переписывание рассматривать только если потолок останется после треков 1–3 и
  только по измеренному профилю. Стоимость — дублирование model-call, retries, agent
  loop, MCP клиента, session store, rate limit.
