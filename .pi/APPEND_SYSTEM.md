## codebase-memory

- Имя проекта — только из `codebase-memory_list_projects()`, не угадывать и не выдумывать.
- `name` в `index_repository` не передавать: без него имя выводится из пути и не плывёт между агентами; `repo_path` — абсолютный. После существенных правок кода — переиндексация.
- Поиск даёт 0 там, где код точно есть, или в графе < 100 узлов — индекс битый: `delete_project` и индексация заново.
- Классы, структуры, глобальные переменные, типы — искать графом (`search_graph`): быстрее и точнее grep (BM25 + camelCase-сплит + буст определений, без ложных срабатываний на использования).
- Кто вызывает X / цепочки между сервисами — `trace_path` с `mode: "cross_service"`; но HTTP-адресацию из env/конфига он не резолвит — такие связки добирать доками (doc/api-flow.md) и e2e-тестами.
- Граф не для конфигов (.env, compose, Makefile), документации, логов, shell-скриптов и runtime-динамики — там `rg`.

## subagent

**Research fanout — главный сценарий.** Параллельные `scout`/`researcher` с разными углами (README сервисов, doc/, compose, тесты, код) собирают то, что граф не соединяет: доки↔код, семантику ответственности между микросервисами, контуры «кто за что отвечает». Граф силён внутри одного языка/сервиса (точные CALLS, трассы, сниппеты); кросс-сервисные вопросы — fanout + синтез в parent. В task-промпте ребёнка можно рекомендовать конкретные доки/пути как стартовые точки — без пересказа содержимого: дети с тем же cwd читают AGENTS.md сами.

**Делегировать мелочь — норм.** Небольшие самодостаточные задачки (даже с мини-расследованием) стоит отдавать субагентам: работа ребёнка не засоряет родительский контекст, результат легко проверить по git diff, а parent сохраняет чистый контекст для декомпозиции следующего шага — так задача и контекст делятся на этапы (pipeline).

- Встроенные роли: `scout` (рекон кода), `researcher` (веб/доки с источниками), `worker` (реализация), `reviewer` (ревью), `oracle` (forked second opinion, только advisory), `delegate`. Свои — `.pi/agents/**/*.md`.
- В промпте ребёнка: цель, cwd/ref, граница правок, критерии приёмки, валидация, формат отчёта. Builtin-дети с тем же cwd сами читают AGENTS.md; критичные запреты проекта (demo `autoparts-store-*`, seed/cleanup demo-базы) переносить в task-промпт только кастомным детям с `inheritProjectContext: false` или одной строкой-напоминанием.
- Oracle только советует, worker пишет после одобренного направления. Детям не спавнить внуков без явного fanout. Mutation-детям не давать жёсткий `toolBudget`.


## Прочее

- **git-commit**: коммиты и push только по явной просьбе пользователя; самостоятельно git только read-only (diff/status/log); не пушить, не аммендить, не `reset --hard`.
- Пакетная обработка файлов/данных — разовый скрипт через `bash` (Python или node), не пачка одинаковых тул-вызовов.
- **playwright** (MCP) — браузер для UI-проверок; **pi-processes** — фоновые долгоживущие процессы (dev-сервер, watcher, логи).
- MCP-граница: подключённые через pi-mcp-adapter внешние MCP (playwright и т.п.) — только для внешних данных и UI. Tenant-данные Helperium — только через собственный mcp-gateway (Streamable HTTP `/mcp`, `X-Tenant-ID`, read-only). Tenant credentials и DSN наружу через внешние MCP не прокидывать.
