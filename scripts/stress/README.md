# scripts/stress — нативный стенд для замеров ёмкости

Это операционная карта стенда: как поднять, как прогнать, и **почему именно так**.
Отвечает на вопрос «что запустить», а не «как устроен прибор».

| Куда идти | Зачем |
|---|---|

| `doc/stress/RUN-*.md` | датированные замеры: что нашли и на каком коммите |

## Что это такое

Четыре процесса на loopback, **не Docker**:

| Процесс | Порт | Чем поднимается |
|---|---:|---|
| data-service | 8084 | Go-бинарь `services/data-service/bin/data-service` |
| mcp-gateway | 8083 | Go-бинарь `services/mcp-gateway/mcp-gateway` |
| api-service | 8081 | `python -m api_service.server`, uvicorn с `--workers $API_WORKERS` |
| стаб LLM | 9099 | `agent-db-stress stub` — **не SUT, а часть прибора** (§4 дизайна) |

**Почему нативно, а не в контейнерах.** Замер ёмкости api-service требует py-spy и
честного CPU-учёта: профилировщику нужен PID процесса, а контейнерный CPU виден только
cgroup-срезом (и на macOS `cgroup_*` вообще не наблюдаем, отчего манифест остаётся
неполным). Нативный процесс отдаёт и профиль, и CPU напрямую. Docker-путь (`compose.sh
--profile test`) описан в RUNBOOK отдельно и решает другую задачу — E2E, не числа ёмкости.

## Три команды

```bash
# 1. поднять/переподнять стенд (идемпотентно; гасит прошлый, собирает бинари,
#    генерирует ключ, проверяет Redis, сидит тенантов, создаёт агента, гоняет preflight)
export PATH="$HOME/.local/bin:$PATH"          # uv из пользовательского инсталлятора
export API_WORKERS=8                          # сколько ядер отдать api-service
export SESSION_STORAGE_URI=redis://127.0.0.1:6379/0
export LLM_PROVIDER_TRANSPORT=direct
./scripts/stress/start-stand.sh

# 2. прогнать лестницу (выбрать вариант из таблицы ниже)
./scripts/stress/run-l2.sh

# 3. погасить
./scripts/stress/stop-stand.sh
```

`start-stand.sh` завершается **ненулевым кодом, если preflight отказал**: «стенд поднят»
означает «стенд способен прогнать профиль», а не «процессы запустились».

Останавливать нужно именно `stop-stand.sh` (или повторный `start-stand.sh`): он гасит
процессы **по портам**, а не только по pid-файлам, потому что uvicorn с `--workers`
плодит воркеров, и pid-файл хранит только родителя.

## Варианты прогонов

| Скрипт | Слой | Что меряет | Профиль | Rates |
|---|---|---|---|---|
| `run-l1.sh` | L1 | MCP → gateway → data-service, **без LLM** | `mcp-tool-call-l1` | 5…80 |
| `run-l1-high.sh` | L1 | потолок платформы, шире | тот же | 80…1280 |
| `run-l1-relieved.sh` | L1 | то же, но с разгруженным генератором | тот же | 80…1280 |
| `run-l2.sh` | L2 | чат через api-service, стаб ~0 мс | `chat-zero-latency-l2` | 5…80 |
| `run-l2-realistic.sh` | L2 | чат со «секундным» стабом и чанками | `chat-slow-l2` | 5…40 |
| `diag-zombies.sh` | — | Живёт ли ход после отвала клиента (гипотеза зомби, опровергнута) | — | 40 |

**Когда какой L1.** Начинать с `run-l1.sh`. Если верхние ступени уходят в `invalid` при
`gen CPU >= 80%` — это **потолок прибора, а не платформы**: брать `run-l1-relieved.sh`,
который ужимает пул воркеров (`--pool-margin-s 0.05 --max-pool-expansions 0`), потому что
каждый воркер несёт busy-wait хвост своего тика и широкий пул сжигает ядро генератора
раньше, чем достигается платформа.

**Когда какой L2.** `run-l2.sh` — «чистый» потолок api-service (стоимость стаба вычтена).
`run-l2-realistic.sh` — то же при реалистичной подложке: секундные ответы и доставка тела
чанками. Бюджет у них **разный и это осознанно**: 500 мс против 8500 мс, потому что в
judged-метрику L2 входит время стаба, а при p50 2 с ход занимает 5–8 с — с T=500 мс каждая
ступень падала бы из-за модели, а не из-за платформы.

## Переменные, которые меняют замер

Единственный источник — [`stand.env`](stand.env); `run-*.sh` его сорсят. Эти же значения
читает api-service на старте, поэтому менять их нужно **до** `start-stand.sh`.

| Переменная | Дефолт | Что делает | Почему важно |
|---|---|---|---|
| `API_WORKERS` | `1` | число uvicorn-воркеров | распараллеливает agent loop по ядрам; откат — `1` |
| `LLM_PROVIDER_TRANSPORT` | `litellm` | `direct` = httpx мимо litellm | снимает ~55% CPU/вызов с горячего пути |
| `SESSION_STORAGE_URI` | пусто | пусто = SQLite; `redis://…` = Redis | убирает SQLite WAL из горячего пути |
| `RATE_LIMIT_STORAGE_URI` | пусто | бэкенд slowapi-лимитера | пусто = in-memory (**на N воркерах лимит станет N×**) |
| `ABUSE_STORAGE_URI` | пусто | бэкенд abuse-бакетов | то же |
| `ABUSE_MAX_USER_TURNS` | `1000000` | квота ходов на сессию | **серверный дефолт 50 — ложный потолок**, см. грабли |
| `CHAT_RATE_LIMIT` | `60000/minute` | slowapi на путь чата | дефолт 30/minute = 0.5 rps |
| `MCP_RATE_LIMIT_RPS` / `_BURST` | `1000` | лимит шлюза | дефолт 10 rps |
| `ABUSE_IP_RPS` / `_BURST` | `1000` | per-IP бюджет | дефолт мал для лестницы |
| `STUB_P50_MS` / `_P95_MS` | `1` / `5` | задержка стаба | задаёт «скорость» модели |
| `STUB_RESPONSE_CHUNKS` / `_CHUNK_DELAY_MS` | `1` / `0` | доставка тела | `300`/`2` = реалистичный профиль |

**Ловушка N× лимита.** Пока `RATE_LIMIT_STORAGE_URI`/`ABUSE_STORAGE_URI` пусты, каждый
воркер держит свой in-memory бакет, и суммарный лимит растёт как N×. Лестница прочтёт это
как «платформа стала быстрее», хотя это просто N-кратный лимит. Redis делает бакет общим.

## Флаги харнесса, без которых прогон непубликуем

Эти флаги **ничего не настраивают** — они *записывают* в манифест то, чем стенд был на
самом деле. Забыть их = получить прогон с блокером публикации в отчёте.

| Флаг | Зачем | Если забыть |
|---|---|---|
| `--api-workers N` | сколько воркеров реально было | манифест запишет `1`, и число не привязано к конфигурации |
| `--binary LABEL=PATH[:SOURCE_ROOT]` | провенанс Go-бинарей (§6) | блокер `no runtime artefact is recorded`; бинарь старше своих `.go` отвергается как `stale` |
| `--budget NAME=VALUE` | какой лимит реально стоял (§5) | preflight возьмёт дефолт (10 rps) и напечатает `caps_the_ladder: true` — манифест опишет не тот лимитер |

**`--api-workers` — это декларация, а не настройка.** Воркеры задаёт `API_WORKERS` при
`start-stand.sh`; флаг лишь фиксирует число в манифесте. Рассогласование = вранье в
артефакте. Сейчас ни один `run-*.sh` его не передаёт, поэтому по умолчанию нативный прогон
непубликуем. Остальные флаги пробрасываются в CLI, так что объявить их можно прямо здесь:

```bash
./scripts/stress/run-l2.sh --api-workers 8 \
  --binary mcp-gateway=$(pwd)/services/mcp-gateway/mcp-gateway \
  --binary data-service=$(pwd)/services/data-service/bin/data-service:services/data-service/cmd/server
```

## Грабли (каждая стоила прогона)

### 1. Ложный потолок: квота ходов на сессию

**Симптом.** Ступень падает с `err ≈ 11%`, хотя p95 в бюджете. В логе api-service:

```
[ABUSE] request blocked reason=Session user-turn quota exceeded (50 >= 50)
```

**Причина.** Серверный дефолт `ABUSE_MAX_USER_TURNS=50`. Стадия 90 с при 40 rps и пуле в
64 сессии делает ~56 ходов на сессию — упирается в квоту, и лестница читает это как отказ
платформы. Это тот же ложный потолок §5, что и у IP-лимитов.

**Что с этим делать.** `stand.env` ставит `ABUSE_MAX_USER_TURNS=1000000`. Корень не в
стенде: профиль объявляет `recycle_after_turns: 40` (ротировать сессии до лимита), но
раннер это поле не исполняет — оно только валидируется.

### 2. Композитный агент → `SSE_ABORT` на preflight

**Симптом.** `chat_turn: turn ended in error (ErrorClass.SSE_ABORT)` для всех тенантов.

**Причина.** Агент с двумя тенантами (`["stress-1","stress-2"]`) даёт композитный scope:
шлюз публикует префиксные имена `stress-1__db_map`, а скрипт стаба зовёт логическое
`db_map` — стаб отказывает как неоднозначному. Профили L2 объявлены `scope: separate`
(один тенант на scope).

**Что с этим делать.** `start-stand.sh` держит агента однотенантным и делает
**create-or-update**: повторный `POST /api/agents` вернул бы 409 и оставил старый
композитный агент от прошлой сессии — именно так стенд и ломался.

### 3. Порт не отпущен → api-service падает молча

**Симптом.** `api-service did not become healthy`, а в `.data/logs/api.log` — только
старые записи, ни одной новой.

**Причина.** Процесс убит ≠ порт свободен. uvicorn с `--workers` держит сокет всеми
воркерами и закрывает его асинхронно (MCP-сессии, health-чеки, экспорт трейсов). Новый
стенд стартовал раньше и не мог забиндиться.

**Что с этим делать.** `start-stand.sh` ждёт освобождения всех четырёх портов и падает,
если порт всё ещё занят.

### 4. Health стаба — `/health`, а не `/v1/models`

**Симптом.** Скрипт объявляет живой стаб мёртвым.

**Причина.** У стаба нет роута `/v1/models` — только `POST /v1/chat/completions` и
`GET /health`. Проверка на несуществующем роуте молча «не работала».

**Что с этим делать.** Проверять `/health`.

### 5. `gen CPU >= 80%` — это потолок прибора, не платформы

**Симптом.** Ступень `invalid` с `generator_bound: true` и высоким `cpu_share_of_core`.

**Причина.** Каждый воркер генератора busy-wait'ит хвост своего тика. Широкий пул
(например, 672 воркера после пул-даблинга) съедает больше ядра на сами хвосты, чем на
нагрузку — и ступень описывает генератор, а не сервис.

**Что с этим делать.** Не «даблить пул дальше», а разгружать генератор:
`run-l1-relieved.sh` (`--pool-margin-s 0.05 --max-pool-expansions 0`). Гейт ставит
валидность сам, и это правильное поведение, а не помеха.

### 6. Redis, на который переключили бэкенды, не проверяется

**Симптом.** `SSE_ABORT` или тихая потеря состояния при `*_STORAGE_URI=redis://…` на
отсутствующем Redis.

**Что с этим делать.** `start-stand.sh` пингует каждое указанное хранилище и, если есть
`redis-server`, поднимает локальный инстанс; иначе падает с внятным сообщением. Плюс
`flushall` перед прогоном — иначе префлайт видит чужую историю ходов и лимиты.

### 7. `ulimit -n` при широких пулах

На чистой машине `ulimit -n` = 1024, а пул в сотни воркеров + `TIME_WAIT` этого не
переживают:

```bash
bash -c "ulimit -n 65535; ./scripts/stress/run-l1-high.sh"
```

### 8. Долгий прогон умирает вместе с SSH

Лестница идёт минуты; оборванная сессия убьёт прогон и оставит `aborted` в `status.json`:

```bash
setsid nohup bash -c "ulimit -n 65535; ./scripts/stress/run-l2.sh" > ~/l2.log 2>&1 < /dev/null &
```

## Что читать после прогона

Артефакты лежат в `test-results/stress/<run_uuid>/`. Разбор каждого файла — в RUNBOOK,
раздел «Что читать после прогона». Коротко: перцентили считаются **из `raw/*.jsonl`**
(по записи на ход), `generator/*.json` отвечает за валидность ступени, а `report.json`
собирает вердикты и блокеры публикации.

Одиночный прогон — «форма, не ставка»: публикуемое число требует медианы ≥2 повторов knee,
полного манифеста и чистого дерева.
